# プロダクトバックログ

**次に何を作るか**を、依存順に一列で持つ。

## 1. なぜ docs/ の外にあるか

`docs/` は製品を記述する（[文書体系](../docs/README.md)）。バックログは製品ではなく
**作る順番**を記述する。両者は変わる理由が違う——製品の記述は合意が変われば変わり、
バックログはスプリントごとに変わる。混ぜると、順番が変わるたびに仕様が書き換わったように見える。

[risks.md](../docs/product/risks.md) が「バックログを docs/ に置かない」と述べているのは同じ理由である。

`kind: backlog` は [文書体系 §1](../docs/README.md) の四層（要求・要件・仕様・設計）の
**どれでもない**。だから `layer:` を持たない。

## 2. 何がどこの正か

| 事実 | 正 |
| --- | --- |
| ストーリー `STORY-`、エピック `EPIC-`、リリース、MVP 線 | [story-map.md](../docs/product/story-map.md) |
| ユースケース `UC-`、業務ルール `RULE-`、品質水準 `NFR-` | [spec/](../docs/spec/README.md) |
| 集約 `AGG-`、不変条件 `INV-`、設計課題 `ISSUE-` | [design/](../docs/design/README.md) |
| **バックログ項目 `PBI-`、相対サイズ、順序、スプリント割当** | **[product-backlog.md](product-backlog.md)** |

バックログは上の三つを**識別子で参照するだけ**で、本文を写さない
（同じ事実を二か所に書かない／[文書体系 §6.1](../docs/README.md)）。

## 4. 識別子

| 接頭辞 | 意味 | 例 |
| --- | --- | --- |
| `PBI-` | プロダクトバックログアイテム | `PBI-018` |
| `IPBI-` | 初期バックログの項目（分割前の見取り図。実行しない） | `IPBI-07` |

**`PBI-` の番号は不変である。** 並べ替えても番号は変えない。
順序を表すのは [product-backlog.md](product-backlog.md) の「順」列だけである。

## 5. PBI の種別

| 種別 | 何を完成させるか | 受け入れる人 |
| --- | --- | --- |
| **合意** | 顧客 PO と仕様を合意し、チームと AI が設計の認識を揃えるところまで | 顧客 PO（仕様）／チーム（設計） |
| **実装** | 物理設計・コード・自動テスト・手動テストまで。画面で動く | 顧客 PO |
| **基盤** | どの実装 PBI を解錠するかが言える技術的土台 | チーム（PO へは解錠したストーリーで説明する） |

**基盤 PBI は「これがないと着手できない実装 PBI」を挙げられない限り立てない。**
挙げられないものは、価値の PBI の中に埋める。

## 6. 一つの PBI が通る道

要求 `product/` → 顧客 PO と議論して仕様 `spec/` に落とし合意
→ チームと AI で設計 `design/` の認識を合わせる → コード → 自動テスト
→ 必要に応じて手動テスト → 受け入れ基準の充足を確認 → PO が受け入れる

開発初期はこの道を **1 つの PBI で通しきれない**。前半（合意）と後半（実装）に割る。
どこで割るか、割った各々の受け入れ基準に何を書くかは
[policies/splitting.md](policies/splitting.md) と
[policies/acceptance-criteria.md](policies/acceptance-criteria.md) が定める。

## 7. 相対サイズ

基準は **PBI-006（書籍を手入力で登録できる）= M** である。

| サイズ | pt | 目安 | 扱い |
| --- | --- | --- | --- |
| **S** | 1 | 既にある型に沿った追加。1 画面の一部 | |
| **M** | 2 | 標準の一枚。1 つの `UC-` 群、1 画面 | 標準 |
| **L** | 3 | 新しい集約に触れる、複数の `UC-` に跨る | **上限** |
| **XL** | 5 | 1 つでスプリントの大半を塞ぐ | **要分割**。割れない理由を書けたときだけ残す |
| **XXL** | 8 | スプリントに収まらない | **置かない**。[initial-backlog.md](initial-backlog.md) にだけ現れてよい |

**ベロシティ想定は 2 週間スプリントあたり 7〜8 pt。**
スプリントに 3〜4 個の PBI が入り、**1 個も完成しないスプリントが生じない**大きさである。

## 8. 準備完了の定義（DoR）

スプリントに引き込んでよい PBI の条件。

- 対象の `STORY-` と `EPIC-` が特定されている（基盤 PBI は解錠する PBI が挙がっている）
- 受け入れ基準がフェーズの指針に沿って書かれている
- 依存する PBI が完了しているか、同一スプリント内で先に完了する見込みがある
- この PBI を止める優先度 **A** の `Q-` が残っていない（残っているなら合意 PBI が先に来る）
- サイズが **L 以下**である

## 9. 完了の定義（DoD）

すべての PBI に共通する条件。個別の受け入れ基準はこれに**上乗せ**される。

- 受け入れ基準がすべて満たされ、各基準について**誰がどう確かめたか**（自動テスト／手動／読み合わせ）が言える
- 触れた `spec/`・`design/` の記述が、実装と食い違っていない
- 自動テストが CI で通り、増えた範囲が [verified-by-test.md](../docs/design/domain/verified-by-test.md) の `SPEC-` に反映されている
- 作業中に判明した未決は `Q-`、モデルの歪みは `ISSUE-` として起票されている（**残すこと自体は完了を妨げない**）
- 顧客 PO が受け入れた（合意 PBI は「合意できた」ことをもって受け入れとする）

## 10. 読み方

```
今スプリントに何を引くか   → product-backlog.md の上から
なぜこの順番か             → product-backlog.md §3
なぜこの粒度か             → policies/splitting.md
受け入れ基準をどう書くか   → policies/acceptance-criteria.md
この PBI の中身            → items/ の該当リリース
```
