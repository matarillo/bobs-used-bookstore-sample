# R0 — 棚をつくる（15 件 / 31 pt）

**届ける相手は店舗スタッフである。** 市場に向けたリリースではない。
棚に本が載って初めて、R1 で売るものができる（[story-map §6](../../docs/product/story-map.md)）。

局面は **開発初期**。合意 PBI と実装 PBI を分ける
（[splitting.md §1.1](../policies/splitting.md)）。受け入れ基準の書き方は
[acceptance-criteria.md §1・§2](../policies/acceptance-criteria.md) に従う。

> 本書に現れる `UC-` `RULE-` `SCR-` `AGG-` の番号は、仕様と突き合わせるためのアンカーであり、
> **採番の順序も、既に決まっていることも意味しない**（[README §4.1](../README.md)）。
> これらは合意 PBI の**成果として生まれる**。

## PBI-001 — 用語と、R0 で触る範囲の集約の境界を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | —（横断。以後すべての PBI が乗る） |
| サイズ | L |
| 依存 | — |
| 触れる文書 | [glossary.md](../../docs/glossary.md)、[domain/overview.md](../../docs/design/domain/overview.md)、[domain/building-blocks.md](../../docs/design/domain/building-blocks.md) |

**なぜ要るか**: 以後のすべての PBI が、同じ言葉と同じ境界の上で動くようにするため。
言葉が揃っていないと、実装 PBI ごとに「かごは誰のものか」を作り直すことになる。

**受け入れ基準**

- [ ] 店の売買と買取を語るのに要る用語を洗い出して用語集に載せ、顧客 PO と読み合わせて
      「この言葉で話す」と決まっている（読み合わせ）
- [ ] 業務に現れるものを**集約の候補として洗い出し**、`AGG-` として採番した。
      うち **R0 で触るもの**（本・分類・店のスタッフ）について、
      整合性境界——1 つの単位作業で守る範囲——がチームと AI で合意されている（読み合わせ）
- [ ] R0 で触らない集約は、**名前と責務だけ**を置き、属性と不変条件には踏み込んでいない（読み合わせ）
- [ ] 金額と数量の扱い（丸めの向き、負値の可否）が決まり、値オブジェクトとして起きている（読み合わせ）
- [ ] 集約をまたぐ更新が要る箇所が列挙され、各々「同時に守る／結果整合でよい」が決まっている（読み合わせ）
- [ ] かごの持ち主が誰かという問いが立ち、回答か残置に仕分けされている。
      残置なら `ADR-` と再訪条件がある（読み合わせ）
- [ ] 決まらなかったことが `Q-` として起票され、優先度が付いている（読み合わせ）

**やらないこと**: 画面もコードも作らない。**R0 で触る範囲だけを `[強制]` まで詰め、
残りは名前と責務に留める**——これが L に収まる条件である
（[splitting.md A2・A5](../policies/splitting.md)）。

## PBI-002 — 画面の共通作法と画面一覧を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | — |
| 触れる文書 | [spec/conventions.md](../../docs/spec/conventions.md)、[spec/screens.md](../../docs/spec/screens.md)、[wireframes/](../../docs/spec/wireframes/README.md) |

**なぜ要るか**: 通知・確認・エラー・空一覧・金額書式は、**個別の PBI で毎回決めると
画面ごとにばらつく**。最初に一度だけ決める、[splitting.md A3](../policies/splitting.md) の例外である。
画面一覧と共通フレームも同じ理由でここに置く——以後の合意 PBI は、
この一覧に `SCR-` を足していく形になる。

**受け入れ基準**

- [ ] 通知・確認・エラー・空の一覧・金額書式・ページ送りの作法が書かれ、
      顧客 PO と読み合わせ済み（読み合わせ）
- [ ] **業務上の失敗の伝え方**について、その場で伝える失敗とエラー画面に落とす失敗の
      線引きが決まっている（読み合わせ）
- [ ] 店頭と管理の**共通フレーム**（ヘッダ・ナビ・通知領域・脚部）のワイヤーフレームを描き、
      ブラウザで PO と読み合わせて合意した（読み合わせ）
- [ ] 画面一覧に、R0 で作る `SCR-` と、匿名で到達できる画面の区別が置かれている（読み合わせ）
- [ ] 作法が **画面名を挙げずに書ける形**になっており、以後の実装 PBI の受け入れ基準から
      識別子で参照できる（読み合わせ）

**やらないこと**: 個々の業務画面の版面。それは各機能の合意 PBI が持つ。

## PBI-003 — 1 本通る土台と層の規約をつくる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | L |
| 依存 | PBI-001 |
| 解錠する PBI | PBI-006（最初の実装 PBI）、以後のすべての実装 PBI |
| 触れる文書 | [design/architecture.md](../../docs/design/architecture.md) |

**なぜ要るか**: 「どの実行単位のどの層に何を置くか」が決まっていない状態では、
すべての実装 PBI の見積りが当て推量になる（[initial-backlog.md §3.2](../initial-backlog.md)）。
**型を作ることがこの PBI の価値である。**

**受け入れ基準**

- [ ] 層の分け方（画面 / ユースケース手順 / ドメイン / 永続化）と、各層をどのプロジェクトに
      置くかの規約を決め、`architecture.md` に記した（読み合わせ）
- [ ] 1 つの画面要求が、その層をすべて通って返る（自動）
- [ ] 名前空間・クラスの置き場・テストの置き場の規約が決まり、
      **AI への指示だけで正しい場所に置けること**を 1 例で確かめた（手動）
- [ ] 単位作業が要求 1 件につき 1 つ共有される（自動）
- [ ] **スキーマはマイグレーションで管理され、既存のデータを消さずに更新できる。**
      「想定と違えば作り直す」経路を作らない（自動）
- [ ] ローカルでの起動手順が 1 ページに収まっている（手動）

**やらないこと**: 業務機能を作らない。土台の確認に使った画面は捨てる。

## PBI-047 — 自動テストと CI の型をつくる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-003 |
| 解錠する PBI | PBI-005・PBI-053（安全の `NFR-` を自動で固定する）、以後すべての実装 PBI |

**なぜ `PBI-003` と分けるか**: 土台が通ることと、**それを自動で確かめ続けられること**は別である。
`PBI-005` 以降の受け入れ基準は「匿名で到達できる画面が一致する（自動）」のように
**要求のレベルで確かめる**ことを求めており、集約とコントローラの単体テストだけでは書けない。
どのレベルのテストをどこに置くかを決めるのがこの PBI である。

**受け入れ基準**

- [ ] テストの層（ドメインの単体 / 手順の単体 / 要求レベルの通し）を決め、
      それぞれの置き場と書き方の見本が 1 本ずつある（読み合わせ）
- [ ] **要求レベルのテスト**が書ける——認証・権限・偽造要求の検証を、
      画面を経る形で確かめられる（自動）
- [ ] 構成をコードで定義した部分（`PBI-010`・`PBI-055`）も、
      **期待する構成になっているかを自動で確かめられる**（自動）
- [ ] CI でビルドと全テストが走り、失敗が赤で出る。**赤のまま次へ進めない**（自動）
- [ ] テストで固定した範囲を `SPEC-` として記録する場所と、更新の作法が決まっている（読み合わせ）

## PBI-044 — 共通フレームと既定の画面をつくる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-003 |
| 解錠する PBI | 画面を持つすべての実装 PBI |
| 画面 | 店頭・管理の共通フレーム、エラー画面、プライバシー画面 |

**なぜ要るか**: `PBI-002` で合意した作法——通知の出し方、エラーの見せ方、空の一覧——は、
**置き場が無ければ画面ごとに書かれる**。最初の実装 PBI より前に、共通の器を作る。
エラー画面とプライバシー画面は、どの機能にも属さないがどの機能からも遷移しうるため、
ここで作らないと誰も作らない。

**受け入れ基準**

- [ ] 店頭と管理の共通フレーム（ヘッダ・ナビ・通知領域・脚部）が、
      `PBI-002` で合意したワイヤーフレームのとおりに描かれている（手動）
- [ ] `PBI-002` で決めた通知・確認・空の一覧の作法が、
      **各画面が呼ぶだけで使える形**になっている（読み合わせ）
- [ ] 想定外の失敗が起きたとき、店頭と管理のそれぞれでエラー画面に落ち、
      内部の詳細が漏れない（自動）
- [ ] プライバシー画面が匿名で到達でき、画面一覧と一致する（自動）
- [ ] 画面の資材（スタイル・スクリプト）の置き場と配信の仕方が決まっている（読み合わせ）

      画面を経る形で確かめられる（自動）

- [ ] [型] 上の安全に関する `NFR-` を固定する自動テストがある——
      **`[強制]` を掲げて検証しない状態を作らない**（[non-functional.md §4](../../docs/spec/non-functional.md)）（自動）

## PBI-009 — 【店】本の状態が伝わる写真を載せられる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | **STORY-23**（`STORY-07` から分けた付加価値） |
| サイズ | M |
| 依存 | PBI-006 |

**なぜ R0 か**: 中古本は 1 冊ごとに状態が違う（`STORY-03` の理由、`HYP-04`）。
写真は品定めの材料である。顧客が見るのは R1 からだが、**棚入れと同時に撮る方が
二度手間にならない**——R0 で数百冊を打ち込んだ後に、もう一度棚から出して撮り直す
ことになる。この業務側の理由で R0 に置く。

**R0 の範囲はアプリの内側に保管するところまで。** 外部の保管・配信と適正判定は
`PBI-054`（R1）である。R0 で写真を見るのは店のスタッフだけであり、
配信の速さも公開時の適正判定もまだ効かない。

**受け入れ基準**

- [ ] 表紙画像を登録すると、在庫詳細に表示される（自動）

## PBI-010 — ネットワークとデータベースを作る

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-047 |
| 解錠する PBI | PBI-055（アプリの配備） |
| 触れる文書 | [architecture.md](../../docs/design/architecture.md)、[ADR-0004](../../docs/design/decisions/ADR-0004-ec2-lift-and-shift.md) |

**なぜ `PBI-055` と分けるか**: 置き場（ネットワークとデータベース）と、
その上で動くもの（アプリの配備）は変わる理由が違う。前者はほぼ変わらず、
後者はリリースのたびに動く。**一緒にすると、毎リリース全体を作り直すことになる。**

**受け入れ基準**

- [ ] 本番相当のネットワークとデータベースの構成を決め、
      その理由とともに `architecture.md` と `ADR-` に記した（読み合わせ）
- [ ] 構成がコードで定義され、**同じものを何度でも作り直せる**（自動）
- [ ] 構成が期待どおりであること（データベースが外から直接見えない等）を
      自動で確かめられる（自動 / `PBI-047` の型に従う）
- [ ] データベースの資格情報がリポジトリと設定ファイルに存在せず、実行時に取得される（自動）
- [ ] 実行単位が 1 つであり停止すれば店が閉まること、障害時にどこまで失うかが
      PO に伝わり、**受容されている**（読み合わせ）

**やらないこと**: バックアップと復旧の作り込みは `PBI-042`（R4、条件付き）。
ここでは**何を受容したかを PO と確認する**。

## PBI-055 — 本番相当へ配備し、繰り返せる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | L |
| 依存 | PBI-010, PBI-053 |
| 解錠する PBI | R0 の店への引き渡しそのもの、および以後**すべてのリリース** |
| 触れる文書 | [architecture.md §3.1](../../docs/design/architecture.md) |

**なぜ要るか**: R0 は**店舗スタッフに届けるリリース**である。動く環境が無ければ届かない。
そして R1 以降も同じ手で配備する——**ここで繰り返せる形にしておかないと、
リリースのたびに手作業が生えて、リリース間隔がそれに律速される。**

**受け入れ基準**

- [ ] ビルド → テスト → 配備が**一つの手順で実行でき、途中で人手が要らない**（自動）
- [ ] 平文でアクセスされた要求は暗号化された経路へ誘導され、
      **平文のまま完結する応答が存在しない**（自動）
- [ ] アプリが異常終了しても再び立ち上がる（手動）
- [ ] 配備の記録（いつ・何を出したか）が残り、**どの版が動いているかが分かる**（手動）
- [ ] スタッフが実際の URL でログインし、本を 1 冊登録できる（手動）
- [ ] **同じ手順を 2 回続けて実行しても壊れない**ことを確かめた（手動）
