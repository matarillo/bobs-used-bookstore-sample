# R0 — 棚をつくる（PBI-001〜010）

**届ける相手は店舗スタッフである。** 市場に向けたリリースではない。
棚に本が載って初めて、R1 で売るものができる（[story-map §6](../../docs/product/story-map.md)）。

局面は **開発初期**。合意 PBI と実装 PBI を分ける
（[splitting.md §1.1](../policies/splitting.md)）。受け入れ基準の書き方は
[acceptance-criteria.md §1・§2](../policies/acceptance-criteria.md) に従う。

---

## PBI-001 — ドメインの骨格と用語を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | —（横断。以後すべての PBI が乗る） |
| サイズ | L |
| 依存 | — |
| 触れる文書 | [glossary.md](../../docs/glossary.md)、[domain/overview.md](../../docs/design/domain/overview.md)、[domain/building-blocks.md](../../docs/design/domain/building-blocks.md) |

**なぜ要るか**: 以後のすべての PBI が、同じ言葉と同じ境界の上で動くようにするため。
ここで境界を決めておかないと、実装 PBI ごとに「かごは誰のものか」を作り直すことになる。

**受け入れ基準**

- [ ] 売買と買取を語るのに要る用語が [glossary.md](../../docs/glossary.md) に揃い、
      顧客 PO と読み合わせて「この言葉で話す」と決まっている（読み合わせ）
- [ ] `AGG-BOOK` / `AGG-CART` / `AGG-ORDER` / `AGG-OFFER` / `AGG-CUSTOMER` /
      `AGG-ADDRESS` / `AGG-REFDATA` が置かれ、**整合性境界**（1 つの単位作業で守る範囲）が
      チームと AI で読み合わせ済み（読み合わせ）
- [ ] `VO-MONEY` / `VO-QUANTITY` と単位作業の扱いが決まっている
      （`RULE-MONEY-01` の丸め方向を含む）（読み合わせ）
- [ ] 集約をまたぐ更新が要る箇所が列挙され、各々「同時に守る／結果整合でよい」が決まっている（読み合わせ）
- [ ] `Q-01`（かごは誰のものか、優先度 **A**）が回答か残置に仕分けされ、残置なら `ADR-` と
      再訪条件がある（読み合わせ）
- [ ] 決まらなかったことが `Q-` として起票され、優先度が付いている（読み合わせ）

**やらないこと**: 画面もコードも作らない。**R0 で触る範囲（書籍・参照データ・顧客）だけを
`[強制]` まで詰め、残りの集約は名前と責務に留める**——これが L に収まる条件である
（[splitting.md A2](../policies/splitting.md)）。

- [ ] 単位作業が HTTP リクエスト 1 件につき 1 つ共有される（自動）
- [ ] CI でビルドと自動テストが走り、失敗が赤で出る（自動）

## PBI-005 — 本人確認と権限を通す

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | L |
| 依存 | PBI-003 |
| 解錠する PBI | PBI-006（管理ポータル）、PBI-018・PBI-031（顧客の本人確認） |
| 触れる文書 | [integrations.md](../../docs/spec/integrations.md) の `EXT-AUTH`、[non-functional.md](../../docs/spec/non-functional.md) |

**なぜ要るか**: 管理ポータルは `Administrators` を要求する（`RULE-ACCESS-02`）。
権限が通っていない状態で登録画面を作ると、**誰でも棚を書き換えられる状態を本番に出す**ことになる。

**受け入れ基準**

- [ ] スタッフが管理ポータルにログインでき、`Administrators` でない利用者は到達できない
      （`NFR-SEC-03` / `RULE-ACCESS-02`）（自動）
- [ ] 匿名で到達できる画面が [screens.md](../../docs/spec/screens.md) の一覧と一致する
      （`NFR-SEC-02`）（自動）
- [ ] すべての更新要求に CSRF 検証が既定で効く（`NFR-SEC-04`）（自動）
- [ ] 開発は擬似認証、本番相当は `EXT-AUTH` で動き、**業務コードは差を知らない**（読み合わせ）
- [ ] `Q-31`（スタッフの役割は一種類でよいか）が回答か残置に仕分けされている（読み合わせ）
- [ ] [型] 上の `[強制]` な `NFR-SEC-*` を固定する自動テストがある——
      **`[強制]` を掲げて検証しない状態を作らない**（[non-functional.md §4](../../docs/spec/non-functional.md)）（自動）

## PBI-009 — 【店】本の状態が伝わる写真を載せられる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | **STORY-23**（`STORY-07` から分けた付加価値） |
| サイズ | M |
| 依存 | PBI-006 |
| 外部連携 | `EXT-IMG-STORE`, `EXT-IMG-CHECK` |

**なぜ R0 か**: 中古本は 1 冊ごとに状態が違う（`STORY-03` の理由、`HYP-04`）。
写真は品定めの材料であり、顧客が見るのは R1 からだが、**棚入れと同時に撮る方が
二度手間にならない**という業務側の理由で R0 に置く。

**受け入れ基準**

- [ ] 表紙画像を登録すると、在庫詳細に表示される（自動）
- [ ] [`NFR-SEC-06`] `EXT-IMG-CHECK` の禁止カテゴリに該当する画像は拒否され、配信されない（自動）
- [ ] [異常系] 画像判定が失敗したとき、書籍の登録内容が失われない（手動）
- [ ] [型] 保管・判定・縮小の**インターフェースをドメイン層が宣言**し、`Bookstore.Data` が
      実装を与える。ドメインは AWS を知らない（[architecture.md §4](../../docs/design/architecture.md)）（読み合わせ）
- [ ] ローカル実行では常に適正と判定され、開発に外部依存が要らない（手動）

## PBI-010 — 本番相当の環境へ配備できる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |

| 触れる文書 | [architecture.md §3.1](../../docs/design/architecture.md)、[ADR-0004](../../docs/design/decisions/ADR-0004-ec2-lift-and-shift.md) |

**なぜ要るか**: R0 は**店舗スタッフに届けるリリース**である。動く環境が無ければ届かない。

**受け入れ基準**

- [ ] CDK の 4 スタック（Core / Network / Database / EC2）で環境が作られ、
      [architecture.md §3.1](../../docs/design/architecture.md) の一覧と一致する（自動）
- [ ] [`NFR-SEC-01`] 平文 HTTP で来た要求は HTTPS へ誘導され、
      **平文のまま完結する応答が存在しない**（自動）
- [ ] [`NFR-SEC-05`] DB 資格情報がリポジトリと設定ファイルに存在せず、
      実行時に `EXT-CONFIG` から取得される（自動）
- [ ] スタッフが実際の URL でログインし、本を 1 冊登録できる（手動）
- [ ] [`NFR-DATA-01`] **DB の自動バックアップが無効であること**が PO に伝わり、
      `RISK-06` として受容されている（読み合わせ）
- [ ] [`NFR-AVAIL-01`] 実行単位が 1 つであり停止すれば店が閉まることが PO に伝わっている（読み合わせ）

**やらないこと**: バックアップの有効化は `PBI-042`（R4）。ここでは**受容されている状態を作る**。
