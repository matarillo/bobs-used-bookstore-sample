# R2 — 注文と配送先を自分で整えられる（8 件 / 15 pt）

局面は **開発中期**。1 PBI = 1 垂直スライスであり、合意は PBI の中に含まれる
（[splitting.md §2](../policies/splitting.md)）。
受け入れ基準は **ユーザーが観測できる振る舞いだけ**を書き、層・置き場は書かない
（[acceptance-criteria.md §3](../policies/acceptance-criteria.md)）。

**新しい画面が増える PBI は、その版面のワイヤーフレームを描いて読み合わせる。**
中期でも画面の合意は要る。変わるのは、合意が別の PBI ではなく**この PBI の中で**行われることだけである。

> **ここに書いてある基準は、読み合わせに持ち込む案である。**
> 中期は仕様の合意が PBI の中にあるため、問いへの回答しだいで基準の文言が変わる。
> スプリント前半の読み合わせで確定させ、確定した文言でスプリントを終える。

## PBI-024 — 注文を取り消せる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-09 |
| サイズ | M |
| 依存 | PBI-023 |
| UC- | `UC-CUST-20` |
| 読み合わせる問い | **取り消せない注文をどう扱うか、確認を挟むか、出荷後の申し出を業務としてどう受けるか** |

**なぜ M か**: 取消は在庫を戻す。**金と在庫が同時に動く数少ない顧客操作**である。
`PBI-015` で「取り消せるのはどこまでか」は決めているが、
**取り消せないと分かっている注文を画面でどう扱うか**はここで決める。

**受け入れ基準**

- [ ] [`UC-CUST-20`] `PBI-015` で合意した状態の注文を取り消すと、取消済になる（自動 / `SPEC-ORDER`）
- [ ] [`RULE-STOCK-02`] 取消が成立したとき在庫が戻る。**成立しなかったときは戻らない**（自動）
- [ ] [`RULE-SERVICE-05`] 取消はべき等である——同じ注文をもう一度取り消しても
      エラー画面に落ちない（自動）
- [ ] 取り消せない注文に対する見せ方が、合意したとおりになっている（手動）
- [ ] [`RULE-ACCESS-01`] 他人の注文番号を指定しても取り消されず、その旨が伝わる（自動）
- [ ] 取消の前に確認を挟み、取り消せたことが画面で分かる（手動）

## PBI-028 — 同時操作の競合をその場で伝える

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-024 |

**なぜ要るか**: 何をその場で伝え、何をエラー画面に落とすかの線引きは `PBI-002` で決めた。
ここで**実際に画面へ適用する**。現場が日常的に踏むのは同時操作の競合であり、
理由が伝わらないままでは運用できない。

**受け入れ基準**

- [ ] 顧客が取り消そうとした注文を、店が先に進めていたとき、理由がその場で伝わる（手動）
- [ ] 別のスタッフが先に処理した注文を操作したとき、理由がその場で伝わり、
      **最新の状態が画面に出る**（手動）
- [ ] [`RULE-SERVICE-03/04`] 個別に指定した対象が不在のときと、
      指定しない操作で対象が不在のときの扱いが、合意した規則どおりに分かれる（自動）
- [ ] `PBI-002` で「エラー画面に落とす」と決めた失敗は、**そのままエラー画面に落ちる**（手動）
- [ ] 上の振る舞いを固定する自動テストがあり、退行が検知できる（自動）

## PBI-045 — 一覧のページ送りの型をつくる

| 項目 | 内容 |
| --- | --- |
| 種別 | 基盤 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-003 |
| 解錠する PBI | PBI-029（顧客側の一覧）、および以後のすべての一覧 |

**なぜ今か**: R0・R1 の一覧は短く、誰も困らなかった。R2 で顧客が自分の履歴を見はじめ、
R3 で買取が棚を育てる。**ここから先に作る一覧はすべてページ送りを要する**ので、
最初の一つを作る前に型を決める。

**受け入れ基準**

- [ ] 件数・並び順・現在位置の扱いが**一つの型**にまとまり、
      一覧ごとに書き直さなくてよい（読み合わせ）
- [ ] 型が店頭と管理の**どちらの一覧にも使える**（自動）
- [ ] 件数が多いとき、全件をメモリに読まない（自動）
- [ ] 既存の一覧（在庫・注文）を型に載せ替えても、表示が変わらない（自動）
- [ ] 版面が `PBI-002` で合意したページ送りの作法と一致している（手動）

## PBI-029 — 増えた一覧の並び順とページ送りを揃える

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | —（横断） |
| サイズ | M |
| 依存 | PBI-023, PBI-025, PBI-026, PBI-045 |
| 読み合わせる問い | 件数が増えた一覧をどう見せるか、空の一覧で何を言うか |

**なぜここか**: R2 で顧客が**自分の履歴を見る**ようになって初めて、件数が問題になる。
R1 までは一覧が短く、誰も困らない。

**受け入れ基準**

- [ ] 自分の注文・自分の住所・かご・欲しい物の一覧に、合意した並び順が適用されている（自動）
- [ ] 合意した件数を超えたときの見せ方（ページ送り等）が適用されている（自動）
- [ ] 常連客の注文が多数になっても、一覧から目的の注文にたどり着ける（手動）
- [ ] 空の一覧の文言と誘導が、すべての一覧で揃っている（手動）
