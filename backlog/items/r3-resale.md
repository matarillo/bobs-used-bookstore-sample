# R3 — 店に行かずに本を売れる（PBI-030〜037）

局面は **開発中期**。ただし買取は**新しいサブドメイン**であり、
最も危うい仮説 [HYP-05](../../docs/product/hypotheses.md) と `RISK-01` を抱え、
優先度 **A** の `Q-20` / `Q-21` が未回答である。

[phases.md §5](../policies/phases.md) の条件に三つとも当たるため、
**このストーリー群に限って初期のやり方に戻し、合意 PBI（`PBI-030`）を分けて先に置く。**

---

## PBI-030 — 買取の成立の仕方を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-12, 14 |
| サイズ | M |
| 依存 | PBI-001 |
| 触れる文書 | [customer-resale.md](../../docs/spec/use-cases/customer-resale.md)、[staff-offers.md](../../docs/spec/use-cases/staff-offers.md)、[aggregate-offer.md](../../docs/design/domain/aggregate-offer.md) |

**なぜ要るか**: `HYP-05`（「顧客が希望額を申告し、店は承認か却下だけ」で買取は成立する）は
**現時点で事業を最も脅かす前提**である。外れると買取の流れ全体が回らない。
作ってから確かめるのではなく、**何が起きたら反証とみなすか**を先に決める。

**受け入れ基準**

- [ ] `Q-20`（買取価格は誰が決めるのか、優先度 **A**）に回答が出ている。
      [ADR-0003](../../docs/product/decisions/ADR-0003-defer-counter-offer.md)（カウンターオファー見送り）を
      維持するなら、**再訪条件**が数字で書かれている（読み合わせ）
- [ ] `Q-21`（買取の進行を顧客にどう伝えるか、優先度 **A**）に回答が出ている。
      [ADR-0002](../../docs/product/decisions/ADR-0002-defer-notifications.md)（通知見送り）を維持するなら、
      **顧客が自分で確かめに来る**という前提が `UC-CUST-22` に落ちている（読み合わせ）
- [ ] 買取の状態遷移（承認待ち → 承認済 → 受領確認済 → 支払完了、却下は 2 箇所から）が
      顧客 PO と合意され、`RULE-TRADE-01`〜`06` として採番されている（読み合わせ）
- [ ] `AGG-OFFER` の属性・状態・不変条件がチームと AI で揃い、
      **支払日を独立した属性とする理由**（期間への割り当て／`RULE-PERIOD-05`）が共有されている（読み合わせ）
- [ ] `RISK-01` の監視列が測れる形になっている——
      **承認済のまま滞留するオファーの件数**と**申込 → 支払完了の到達率**を、
      どの画面のどの数字で見るかが決まっている（読み合わせ）
- [ ] `Q-22`（画面の言葉と用語集が食い違う）が解消され、
      買取の用語が [glossary.md](../../docs/glossary.md) と一致している（読み合わせ）

## PBI-031 — 読み終えた本の買取を申し込める

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-12 |
| サイズ | **L** |
| 依存 | PBI-005, PBI-030 |
| UC- | `UC-CUST-21` |
| 画面 | [SCR-RESALE-NEW](../../docs/spec/wireframes/customer/SCR-RESALE-NEW.html) |

**なぜ L か**: 新しい集約 `AGG-OFFER` をここで初めて作る。
R0 で作った型は使えるが、**集約が一つ増えることの税**がかかる。

**受け入れ基準**

- [ ] [`UC-CUST-21`] 顧客が書名・著者・ISBN・分類・希望額を入力して申し込むと、
      承認待ちのオファーができる（自動 / `SPEC-OFFER`）
- [ ] [`RULE-SERVICE-01`] 申込は顧客が存在することを前提とし、未認証では申し込めない（自動）
- [ ] [`RULE-MONEY-01`] 希望額が負や小数で入力されたとき、受け付けられないか丸められる——
      `PBI-030` で合意したとおりになる（自動）
- [ ] [異常系] 入力の不備がその場に出て、入力内容が失われない（手動）
- [ ] [`Q-21` の回答] 申し込んだ後に**顧客が次に何をすればよいか**が画面で分かる
      （現物を送ってよいのはいつか）（手動）

## PBI-036 — 【店】支払済の本に売価を付けて棚に載せられる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-16 |
| サイズ | M |
| 依存 | PBI-006, PBI-035 |
| UC- | `UC-STAFF-16` |

**なぜ要るか**: 買い取った本は**売れて初めて利益になる**（`STORY-16` の理由）。
ここが買取サブドメインと販売サブドメインの唯一の接点である。

**受け入れ基準**

- [ ] [`UC-STAFF-16`] 支払完了の申込に売価を付けて棚入れすると、在庫に書籍が 1 冊できる（自動 / `SPEC-OFFER`）
- [ ] [`RULE-TRADE-01`] **店は買っていない本を売らない**——支払完了でない申込は棚入れできない（自動）
- [ ] [`RULE-TRADE-02`] 二重の棚入れは拒否される（自動）
- [ ] [`RULE-TRADE-03`] 売価は買取価格から自動で導かれず、店が独立に決める（自動）
- [ ] [`RULE-TRADE-04`] 棚入れでできた書籍は仕入原価を持ち、**以後の買取価格の変更に追随しない**（自動）
- [ ] スプリントレビューで「申込 → 承認 → 受領 → 支払 → 棚入れ → 顧客が買える」を
      通しで実演できる（手動）

## PBI-037 — 【店】増えた在庫から目的の本にたどり着ける

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | **STORY-22**（`STORY-07` から分けた付加価値） |
| サイズ | S |
| 依存 | PBI-007, PBI-036 |
| UC- | `UC-STAFF-12`（絞り込み） |

**なぜ R3 か**: 買取が始まると棚が急に育つ。**在庫が数十件のうちは、絞り込みは誰も使わない**
（[splitting.md §4.3](../policies/splitting.md)）。

**受け入れ基準**

- [ ] [`UC-STAFF-12`] 在庫一覧を書名・分類・在庫状態で絞り込める（自動）
- [ ] 絞り込んだ条件が入力欄に残る（手動）
- [ ] [`RULE-STOCK-04`] 在庫僅少（在庫数 ≦ 5、在庫 0 を含む）だけを取り出せる——
      **仕入判断に使える**（自動）
- [ ] 買取由来の本と手入力の本を見分けられる（手動）
