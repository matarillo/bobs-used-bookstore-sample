# R3 — 店に行かずに本を売れる（PBI-030〜037）

局面は **開発中期**。ただし買取は**新しいサブドメイン**であり、
最も危うい仮説 [HYP-05](../../docs/product/hypotheses.md) を抱え、
**買取価格を誰が決めるのか**と**進行を顧客にどう伝えるのか**という
優先度 **A** の問いが未回答である。

[phases.md §5](../policies/phases.md) の条件に三つとも当たるため、
**このストーリー群に限って初期のやり方に戻し、合意 PBI（`PBI-030`）を分けて先に置く。**

---

## PBI-030 — 買取の成立の仕方を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-12, 14 |
| サイズ | M |
| 依存 | PBI-001 |
| 触れる文書 | [customer-resale.md](../../docs/spec/use-cases/customer-resale.md)、[staff-offers.md](../../docs/spec/use-cases/staff-offers.md)、[aggregate-offer.md](../../docs/design/domain/aggregate-offer.md) |

**なぜ要るか**: 「顧客が希望額を申告し、店は承認か却下だけ」で買取は成立する、という
`HYP-05` は**現時点で事業を最も脅かす前提**である。外れると買取の流れ全体が回らない。
作ってから確かめるのではなく、**何が起きたら反証とみなすか**を先に決める。

**受け入れ基準**

- [ ] **買取価格を誰が決めるのか**が決まっている。店が額を提示する仕組みを作らないなら、
      その判断を `ADR-` に残し、**再訪条件を数字で**書いてある（読み合わせ）
- [ ] **買取の進行を顧客にどう伝えるか**が決まっている。通知を作らないなら、
      顧客が自分で確かめに来るという前提が `UC-` に落ちている（読み合わせ）
- [ ] 買取が取りうる状態と、その間をどう進むか（誰がいつ却下できるかを含む）が
      顧客 PO と合意され、`RULE-` として採番されている（読み合わせ）
- [ ] 買取申込・申込一覧・店側の審査画面のワイヤーフレームを描き、
      ブラウザで読み合わせて版面に合意した（読み合わせ）
- [ ] 買取の集約の属性・状態・不変条件がチームと AI で揃い、
      **支払った時点を独立して持つ理由**（金が出た月に支出を割り当てるため）が共有されている（読み合わせ）
- [ ] `HYP-05` の反証を測る指標——**滞留している申込の件数**と**申込から支払完了への到達率**——について、
      どの画面のどの数字で見るかが決まっている（読み合わせ）
- [ ] 買取で使う言葉が用語集と一致している（読み合わせ）

## PBI-031 — 読み終えた本の買取を申し込める

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-12 |
| サイズ | **L** |
| 依存 | PBI-005, PBI-030 |
| UC- | `UC-CUST-21` |
| 画面 | `SCR-RESALE-NEW` |

**なぜ L か**: 買取の集約をここで初めて作る。R0 で作った型は使えるが、
**集約が一つ増えることの税**がかかる。

**受け入れ基準**

- [ ] [`UC-CUST-21`] 顧客が `PBI-030` で合意した項目を入力して申し込むと、
      最初の状態のオファーができる（自動 / `SPEC-OFFER`）
- [ ] [`RULE-SERVICE-01`] 申込は顧客が存在することを前提とし、未認証では申し込めない（自動）
- [ ] 希望額が金額として妥当でない値のとき、`PBI-030` で合意したとおりに扱われる（自動）
- [ ] [異常系] 入力の不備がその場に出て、入力内容が失われない（手動）
- [ ] 申し込んだ後に**顧客が次に何をすればよいか**が画面で分かる
      （現物を送ってよいのはいつか）（手動）
- [ ] 版面が `PBI-030` で合意したワイヤーフレームと一致している（手動）

**受け入れ基準**

## PBI-034 — 【店】検分して承認か却下を決められる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-14 |
| サイズ | M |
| 依存 | PBI-033 |
| UC- | `UC-STAFF-08`, `UC-STAFF-09` |

**受け入れ基準**

- [ ] [`UC-STAFF-08`] 審査待ちの申込を承認すると、発送を待つ状態になる（自動 / `SPEC-OFFER`）
- [ ] [`UC-STAFF-09`] `PBI-030` で合意した状態から却下でき、**現物を見てから断れる**（自動）
- [ ] 支払が済んだ申込と却下した申込は、もう承認できない（自動）
- [ ] [異常系] 別のスタッフが先に裁いた申込を操作したとき、
      `PBI-028` で作った作法どおりに理由が伝わる（手動）

## PBI-035 — 【店】現物の受領と支払を記録できる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-15 |
| サイズ | M |
| 依存 | PBI-034 |
| UC- | `UC-STAFF-10`, `UC-STAFF-11` |

**受け入れ基準**

- [ ] [`UC-STAFF-10`] 承認済の申込に現物の受領を記録できる（自動）
- [ ] [`UC-STAFF-11`] 受領済の申込に支払を記録すると、**支払った時点が残る**（自動）
- [ ] [`RULE-PERIOD-05`] 買取側の支出が、`PBI-030` で合意した基準日で期間に割り当てられる

- [ ] 支払が済んだ申込の買取価格は、後から変えられない（自動）

## PBI-036 — 【店】支払済の本に売価を付けて棚に載せられる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-16 |
| サイズ | M |
| 依存 | PBI-006, PBI-035 |
| UC- | `UC-STAFF-16` |

**なぜ要るか**: 買い取った本は**売れて初めて利益になる**（`STORY-16` の理由）。
ここが買取サブドメインと販売サブドメインの唯一の接点である。

**受け入れ基準**

- [ ] [`UC-STAFF-16`] 支払の済んだ申込に売価を付けて棚入れすると、在庫に書籍ができる（自動 / `SPEC-OFFER`）
- [ ] [`RULE-TRADE-01`] **店は買っていない本を売らない**——支払が済んでいない申込は棚入れできない（自動）
- [ ] [`RULE-TRADE-02`] 同じ申込を二度棚入れできない（自動）
- [ ] [`RULE-TRADE-03`] 売価は買取価格から自動で導かれず、店が独立に決める（自動）
- [ ] [`RULE-TRADE-04`] 棚入れでできた書籍の仕入原価が、以後の買取価格の変更に追随しない（自動）
- [ ] スプリントレビューで「申込 → 承認 → 受領 → 支払 → 棚入れ → 顧客が買える」を
      通しで実演できる（手動）

## PBI-037 — 【店】増えた在庫から目的の本にたどり着ける

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | **STORY-22**（`STORY-07` から分けた付加価値） |
| サイズ | S |
| 依存 | PBI-007, PBI-036 |
| UC- | `UC-STAFF-12`（絞り込み） |

**なぜ R3 か**: 買取が始まると棚が急に育つ。**在庫が少ないうちは、絞り込みは誰も使わない**
（[splitting.md §4.3](../policies/splitting.md)）。

**受け入れ基準**

- [ ] [`UC-STAFF-12`] 在庫一覧を書名・分類・在庫状態で絞り込める（自動）
- [ ] 絞り込んだ条件が入力欄に残る（手動）
- [ ] [`RULE-STOCK-04`] 仕入を判断すべき在庫水準の本だけを取り出せる（自動）
- [ ] 買取由来の本と手入力の本を見分けられる（手動）
