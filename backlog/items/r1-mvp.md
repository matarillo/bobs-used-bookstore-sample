# R1(MVP) — 探して買える／店が届けきれる（PBI-011〜022）

**MVP 線はこのリリースの下にある。** 市場の反応を得るのに最低限必要なのは
「探して・注文できて・店が届けきれる」である（[story-map §6](../../docs/product/story-map.md)）。

局面は **開発初期の後半**。合意 PBI（`PBI-011` / `014` / `015`）はここが最後になる見込みで、
[phases.md §3](../policies/phases.md) の判定条件を **S5 と S6 のレビュー直後**に確認する。
満たしていれば R2 から中期の書き方（[acceptance-criteria.md §3](../policies/acceptance-criteria.md)）へ移る。

## PBI-011 — 探すと品定めの仕様を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-01, 02, 03 |
| サイズ | M |
| 依存 | PBI-004 |
| 触れる文書 | [customer-browse.md](../../docs/spec/use-cases/customer-browse.md)、[read-models.md](../../docs/design/domain/read-models.md) |

**なぜ要るか**: `Q-03`（検索は何を探すのか）は優先度 **A** で、
**決まらないと検索は作れない**と明記されている。照合対象が未定義のまま作ると
`RISK-05`（探しても見つからない体験）を自分で作り込むことになる。

**受け入れ基準**

- [ ] `Q-03` に回答が出ている——**照合対象**（書名／著者／ISBN／概要のどれか）と
      **照合方式**（部分一致か単語単位か）が決まり、`RULE-` として採番されている（読み合わせ）
- [ ] `UC-CUST-01`〜`03` の Boundary を顧客 PO と読み合わせ、
      「この項目で本は選べる」と言質が取れている（読み合わせ）
- [ ] `Q-14`（在庫切れでも「かごに入れる」が押せる、優先度 **A**）の書籍詳細側の扱いが
      決まっている（`RULE-STOCK-05` との関係を含む）（読み合わせ）
- [ ] `Q-05`（「売れ筋」とは何か）——集計の期間・単位・件数——が決まり、
      `RM-BESTSELLERS` の定義がチームと AI で揃っている（読み合わせ）
- [ ] `Q-04`（書籍詳細に書籍種別が出ない）が回答か残置に仕分けされている（読み合わせ）
- [ ] `RISK-05` の監視列（0 件検索の比率、検索からの転換率）が、
      **何をもって測るか**まで決まっている（読み合わせ）

## PBI-014 — かごと注文の仕様を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-04, 05 |
| サイズ | L |
| 依存 | PBI-011 |
| 触れる文書 | [customer-cart.md](../../docs/spec/use-cases/customer-cart.md)、[customer-checkout.md](../../docs/spec/use-cases/customer-checkout.md)、[rules.md](../../docs/spec/rules.md) |

**なぜ L か**: 触れる集約が `AGG-CART` / `AGG-ORDER` / `AGG-ADDRESS` / `AGG-CUSTOMER` の
4 つで、[splitting.md A5](../policies/splitting.md) の上限を超えている。
**金の計算と在庫の引き当てという、この店で最も間違えてはいけない箇所**であり、
ここだけは 1 段大きく取る。

**受け入れ基準**

- [ ] `Q-17`（顧客に見せる金額はどれか、優先度 **A**）に回答が出て、
      `RULE-CART-01/02`・`RULE-ORDER-01`〜`04`・`RULE-MONEY-01` が
      [rules.md](../../docs/spec/rules.md) に採番され、**税率の値が入っている**（読み合わせ）
- [ ] `Q-14`（かごの数量と在庫の見せ方、優先度 **A**）に回答が出ている——
      数量を画面から変えられるか、在庫超過を入れられるか（読み合わせ）
- [ ] `Q-26`（注文完了画面に注文番号がない、優先度 **A**）に回答が出ている（読み合わせ）
- [ ] `UC-CUST-04`・`06`・`07`・`12`・`13`・`15` の Boundary を顧客 PO と読み合わせ、
      「この流れで買える」と言質が取れている（読み合わせ）
- [ ] 注文確定が守るもの——在庫の引き当て（`RULE-STOCK-01/03`）、価格の凍結
      （`RULE-TRADE-05`）、最低 1 明細（`RULE-TRADE-06`）、納品予定日（`RULE-PERIOD-03`）——が
      `AGG-ORDER` の不変条件としてチームと AI で揃っている（読み合わせ）
- [ ] `Q-28`（お金の受け渡しを記録しないでよいか、優先度 **A**）が
      [ADR-0001](../../docs/product/decisions/ADR-0001-defer-online-payment.md) の残置として
      確認され、`RISK-02` の監視列が生きている（読み合わせ）
- [ ] `Q-27`（住所は国内向けか国外向けか）の扱いが決まっている（読み合わせ）

## PBI-019 — 注文を確定し、完了を確認できる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-05 |
| サイズ | **L** |
| 依存 | PBI-016, PBI-018 |
| UC- | `UC-CUST-12`, `UC-CUST-13` |
| 画面 | [SCR-CHECKOUT](../../docs/spec/wireframes/customer/SCR-CHECKOUT.html)、[SCR-CHECKOUT-DONE](../../docs/spec/wireframes/customer/SCR-CHECKOUT-DONE.html) |

**なぜ L か**: 1 つの単位作業の中で、注文の生成・在庫の引き当て・価格の凍結・かごの整理が
同時に起きる。**この店で最も守るべき箇所**であり、割ると単独では受け入れられない
（[splitting.md R2](../policies/splitting.md)）。

**受け入れ基準**

- [ ] [`UC-CUST-12`] 配送先を選んで注文を確定すると、注文が受付待ちで作られる（自動）
- [ ] [`RULE-STOCK-01/03`] 明細の数量が在庫から引かれ、**在庫を超える出庫は拒否される**
      （0 に飽和させない）（自動 / `SPEC-ORDER`）
- [ ] [`RULE-STOCK-06`] 在庫切れで見送られた明細はかごに残る（自動）
- [ ] [`RULE-ORDER-01`〜`04`] 小計 → 税 → 合計の順に導出され、各段階で丸められた金額が
      画面に出る（自動）
- [ ] [`RULE-TRADE-05` / `RULE-PERIOD-03`] 価格・原価が確定し、納品予定日が注文時点 + 7 日になる（自動）
- [ ] [`UC-CUST-13` / `Q-26` の決定] 完了画面に、`PBI-014` で決めた内容が出る（手動）
- [ ] [異常系] 在庫不足で確定できなかったとき、`PBI-002` の作法どおりに理由が伝わる（手動）
