# R1(MVP) — 探して買える／店が届けきれる（PBI-011〜022）

**MVP 線はこのリリースの下にある。** 市場の反応を得るのに最低限必要なのは
「探して・注文できて・店が届けきれる」である（[story-map §6](../../docs/product/story-map.md)）。

局面は **開発初期の後半**。合意 PBI（`PBI-011` / `014` / `015`）はここが最後になる見込みで、
[phases.md §3](../policies/phases.md) の判定条件を **S5 と S6 のレビュー直後**に確認する。
満たしていれば R2 から中期の書き方（[acceptance-criteria.md §3](../policies/acceptance-criteria.md)）へ移る。

> 識別子はアンカーであって、採番順でも既決事項でもない（[README §4.1](../README.md)）。

## PBI-011 — 探すと品定めの仕様を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-01, 02, 03 |
| サイズ | M |
| 依存 | PBI-004 |
| 触れる文書 | [customer-browse.md](../../docs/spec/use-cases/customer-browse.md)、[read-models.md](../../docs/design/domain/read-models.md)、[wireframes/customer/](../../docs/spec/wireframes/customer/) |

**なぜ要るか**: **検索が何を照合するのかが決まらないと、検索は作れない。**
照合対象を決めないまま作ると、「探しても見つからない」体験を自分で作り込むことになる。

**受け入れ基準**

- [ ] 検索が**何を照合し、どう照合するか**（対象の項目と、部分一致か単語単位か）が決まり、
      `RULE-` として採番されている（読み合わせ）
- [ ] 探す・品定めするという来店者の操作を `UC-` として書き起こして採番し、
      その Boundary を顧客 PO と読み合わせて「この項目で本は選べる」と言質が取れている（読み合わせ）
- [ ] トップ・検索結果・書籍詳細のワイヤーフレームを描き、ブラウザで読み合わせて
      版面に合意した。画面一覧に `SCR-` が加わっている（読み合わせ）
- [ ] 在庫が無い本を書籍詳細でどう見せるか、かごに入れられるかが決まっている（読み合わせ）
- [ ] **「売れ筋」の定義**——集計の期間・単位・件数——が決まり、
      読み取りモデルとしてチームと AI の認識が揃っている（読み合わせ）
- [ ] 検索が効いているかを測る指標（0 件検索の比率、検索からの転換率）について、
      **何をどう測るか**まで決まっている（読み合わせ）

## PBI-014 — かごと注文の仕様を決める

| 項目 | 内容 |
| --- | --- |
| 種別 | 合意 |
| STORY- | STORY-04, 05 |
| サイズ | L |
| 依存 | PBI-011 |
| 触れる文書 | [customer-cart.md](../../docs/spec/use-cases/customer-cart.md)、[customer-checkout.md](../../docs/spec/use-cases/customer-checkout.md)、[rules.md](../../docs/spec/rules.md) |

**なぜ L か**: 触れる集約が かご・注文・住所・顧客 の 4 つで、
[splitting.md A5](../policies/splitting.md) の上限を超えている。
**金の計算と在庫の引き当てという、この店で最も間違えてはいけない箇所**であり、
ここだけは 1 段大きく取る。

**受け入れ基準**

- [ ] **顧客に見せる金額がどれか**が決まり、小計・税・合計の導出と丸めが `RULE-` として
      採番され、**顧客が決めた税率が入っている**（読み合わせ）
- [ ] かごの数量と在庫の見せ方が決まっている——数量を画面から変えられるか、
      在庫を超えて入れられるか（読み合わせ）
- [ ] 注文が成立したことを顧客に何で示すかが決まっている（読み合わせ）
- [ ] かご・注文手続き・注文完了・住所登録の `UC-` を書き起こして採番し、
      Boundary を顧客 PO と読み合わせて「この流れで買える」と言質が取れている（読み合わせ）
- [ ] 上記 4 画面のワイヤーフレームを描き、ブラウザで読み合わせて版面に合意した（読み合わせ）
- [ ] 注文確定が守るもの——在庫の引き当て、価格の凍結、明細が空の注文を作らないこと、
      納品予定日の決め方——が注文集約の不変条件としてチームと AI で揃い、
      対応する `RULE-` に**顧客が決めた値が入っている**（読み合わせ）
- [ ] **代金の授受をシステムの外に置く**という判断が PO と確認され、
      未収・行き違いのリスクの監視列が生きている（読み合わせ）
- [ ] 住所を国内向けに限るかという問いの扱いが決まっている（読み合わせ）

## PBI-019 — 注文を確定し、完了を確認できる

| 項目 | 内容 |
| --- | --- |
| 種別 | 実装 |
| STORY- | STORY-05 |
| サイズ | **L** |
| 依存 | PBI-016, PBI-018 |
| UC- | `UC-CUST-12`, `UC-CUST-13` |
| 画面 | `SCR-CHECKOUT`, `SCR-CHECKOUT-DONE` |

**なぜ L か**: 1 つの単位作業の中で、注文の生成・在庫の引き当て・価格の凍結・かごの整理が
同時に起きる。**この店で最も守るべき箇所**であり、割ると単独では受け入れられない
（[splitting.md R2](../policies/splitting.md)）。

**受け入れ基準**

- [ ] [`UC-CUST-12`] 配送先を選んで注文を確定すると、注文が最初の状態で作られる（自動）
- [ ] [`RULE-STOCK-01/03`] 在庫の引き当てが `PBI-014` で合意したとおりに行われ、
      **在庫を超える注文が成立しない**（自動 / `SPEC-ORDER`）
- [ ] [`RULE-STOCK-06`] 在庫が足りずに見送られた明細の行き先が、合意したとおりになる（自動）
- [ ] [`RULE-ORDER-01`〜`04`] 画面に出る金額が、合意した導出順と丸めに従っている（自動）
- [ ] [`RULE-TRADE-05` / `RULE-PERIOD-03`] 価格と原価が確定し、納品予定日が
      合意した規則で決まる（自動）
- [ ] [`UC-CUST-13`] 完了画面に、`PBI-014` で決めた内容が出る（手動）
- [ ] [異常系] 在庫不足で確定できなかったとき、`PBI-002` の作法どおりに理由が伝わる（手動）
