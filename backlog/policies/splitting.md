# PBI の分割指針

**一列に並べられて、スプリント内で終わる大きさにする**ための規則。
局面の定義は [phases.md](phases.md) にある。

## 0. どの局面にも効く規則

| # | 規則 |
| --- | --- |
| R1 | **XXL は置かない。** XL は「割れない理由」を書けたときだけ残す。既定の上限は **L** |
| R2 | 割った後の PBI が **単独で受け入れられる**こと。「A が終わっても B が終わるまで見せられない」なら割り方が悪い |
| R3 | 層で割らない。「画面だけ」「ドメインだけ」の PBI を作らない（**初期の合意 PBI と基盤 PBI だけが例外**） |
| R4 | 割った結果、合計の見積りが増えるのは正常である。**見えていなかった作業が現れただけ**である |
| R5 | 割れないときは順序を疑う。先に置くべき決定が抜けていることが多い |

## 1. 開発初期の分割指針

### 1.1 まず「意思決定の相手」で割る

初期の PBI は、**縦（機能）ではなく、誰と何を決めるかで前後に割る**。

```
 [合意 PBI]                                   [実装 PBI]
 product を基に顧客 PO と議論          →     物理設計を決める
 → spec に落として合意                       → コード
 → design/domain をチームと AI で揃える      → 自動テスト → 手動テスト
                                             → 受け入れ基準の確認 → PO 受け入れ
```

割る位置は **`design/domain` の直後**である。論理設計（技術非依存）までが合意 PBI、
物理設計（どの csproj のどの名前空間に何を置くか）から先が実装 PBI である。

この位置で割る理由は三つある。

1. **論理設計までは、物理設計が未定でも決められる。** 集約の境界と不変条件は
   置き場を知らなくても合意できる（[design/README §2.1](../../docs/design/README.md)）。
2. **合意には顧客 PO の時間が要り、待ちが発生する。** 待ちを実装 PBI の中に抱えると、
   スプリント内で終わらない。
3. **決定は複数の実装 PBI に効く。** 1 対 1 に紐づけると同じ議論を繰り返す。

### 1.2 合意 PBI の切り方

| # | 規則 |
| --- | --- |
| A1 | **1 つの `UC-` グループ（フィーチャー）を単位に切る。** 画面横断で切らない |
| A2 | **在庫を持たない。** 1 つの合意 PBI が支えるのは、**次の 1〜2 スプリントで着手する実装 PBI だけ**。先回りして全部決めない |
| A3 | 例外は**横断的な作法**（通知・確認・エラー・空一覧・金額書式）と**画面一覧**。これは最初に一度だけ決める。個別 PBI で毎回決めると画面ごとにばらつく |
| A4 | 合意 PBI に**コードを含めない。** ただし**ワイヤーフレームは成果物として残す**——画面は文章では合意できず、`SCR-` 1 枚が合意の単位である（[文書体系 §8](../../docs/README.md)、[wireframes/README §1](../../docs/spec/wireframes/README.md)）。使い捨てにしてよいのは、時間軸や状態遷移を確かめるための図だけである（[文書体系 §5.4](../../docs/README.md)） |
| A5 | 触れる集約が 3 つを超えたら割る |
| A6 | **合意 PBI は四つの成果物を必ず持つ**——`UC-`（Boundary の合意）、`RULE-`（顧客が決める値）、`SCR-` のワイヤーフレーム（版面の合意）、`AGG-`/`INV-`（チームと AI の認識合わせ）。どれか一つでも欠けたら、次の実装 PBI は着手できない |

### 1.3 実装 PBI の切り方

| # | 規則 |
| --- | --- |
| B1 | `UC-` の**部分集合**で切る。1 PBI = 1〜3 個の `UC-` |
| B2 | **最初の実装 PBI は 1 段大きく見る。** 物理設計の型を作る税がかかる。型ができた後の同種の PBI は 1 段小さくなる |
| B3 | 「登録できる」→「一覧できる」→「更新できる」の順に割る。**作れないものは見られないし、直せない** |
| B4 | 外部連携（`EXT-`）に触れる部分は別 PBI にする。失敗の見え方の作り込みが本体より大きくなりがちである |
| B5 | 初期に限り、**設計制約を受け入れ基準に書いてよい**（[acceptance-criteria.md §3](acceptance-criteria.md)）。型が守られていることが、この時期の成果そのものだからである |

### 1.4 基盤 PBI の切り方

| # | 規則 |
| --- | --- |
| C1 | **解錠する実装 PBI を挙げられない基盤 PBI は立てない** |
| C2 | 「あとで要るから今作る」は却下する。**最初にそれを必要とする実装 PBI の直前**に置く |
| C3 | 基盤 PBI も PO に説明する。説明の言葉は技術ではなく、**解錠したストーリー**である |

## 2. 開発中期の分割指針

型が決まった後は、**1 PBI = 1 垂直スライス**に戻す。合意は PBI の中に含める。

| # | 規則 |
| --- | --- |
| D1 | 1 PBI で UI → アプリケーション → ドメイン → 永続化を貫く |
| D2 | 仕様の合意は PBI 内で行う。スプリント前半に PO と読み合わせ、後半で作る |
| D3 | L を超えたら `UC-` 単位で割る。それでも超えたら §4 のストーリー分割へ |
| D4 | [phases.md §5](phases.md) の条件に当たるストーリー群は、中期でも合意 PBI を分ける |

## 3. 開発後期の分割指針

| # | 規則 |
| --- | --- |
| E1 | **1 PBI = 1 つの `NFR-`。** 「性能を上げる」ではなく「`NFR-PERF-01` を規定して満たす」 |
| E2 | 「規定しない」と決めた `NFR-` を昇格させる PBI は、**測る**と**満たす**を分けてよい。測って基準内なら、満たす側は捨てられる |
| E3 | 運用手順（復旧・移行）は**実演で終わる**ように切る。手順書だけの PBI を作らない |

## 4. それでも大きいとき — ストーリーをコア価値と付加価値に割る

PBI をどう割ってもサイズが収まらないとき、原因は PBI ではなく**ストーリーが大きい**ことにある。
このときだけ、要求層に戻って `STORY-` を割る。

### 4.1 割ってよい合図

- 1 つの `STORY-` から出る PBI の合計が **1 スプリントの容量（[README §7.1](../README.md)）を超える**
- その PBI 群が**複数のリリースに散る**——ストーリーが「完成」しないので、リリース計画の単位に使えない
- 「この `UC-` を落としても、ストーリーの一文は成立するか」に **成立する**と答えられる

### 4.2 割り方

**削るのではなく、価値を二段に分ける。**

- **コア価値** — ストーリーの一文（〜したい、なぜなら〜）が**成立する最小**。これが欠けると価値がゼロになる
- **付加価値** — コアが届いた後に**効きはじめる**もの。多くは「量が増えたとき」「慣れたとき」に効く

### 4.3 この店で実際に割ったもの

`STORY-07`（手元の本を登録して棚に載せたい）は、PBI に割っても合計が
1 スプリントの容量に迫り、しかも `R0`・`R3`・`R4` の三つのリリースに散る。
**どのリリースでも完成しないので、リリース計画の単位に使えない。**

| 分割後 | 価値 | 派生 `UC-` | リリース |
| --- | --- | --- | --- |
| `STORY-07`（コア） | 本が棚に載る。**載っていない本は売れない** | `UC-STAFF-12〜15` | R0 |
| `STORY-23`（付加） | 状態が写真で伝わる。中古本の品定めの材料になる | `UC-STAFF-14, 15`（画像）, `UC-CUST-03`（表示） | R0 |
| `STORY-22`（付加） | 棚が育っても目的の本にたどり着ける | `UC-STAFF-12`（絞り込み） | R3 |
| `STORY-18`（既存） | 分類の選択肢を店が増やせる | `UC-STAFF-17〜19` | R4 |

**割った付加価値は、それが効き始めるリリースへ置く。**
`STORY-22`（絞り込み）を R3 に置いたのは、買取（`EPIC-RESALE`）が始まると
棚が急に育ち、そこで初めて絞り込みなしでは在庫を扱えなくなるからである。
R0 に置いても、在庫が数十件のうちは誰も使わない。

`STORY-23`（写真）は R0 に残した。棚入れと同時に撮る方が二度手間にならないという
**業務側の理由**であり、実装の都合ではない。

### 4.4 割ってはいけない割り方

| 悪い割り方 | なぜ悪いか |
| --- | --- |
| 「画面だけ先に作る」 | 単独で受け入れられない（R2 違反）。デモしても嘘になる |
| 「バリデーションは後で」 | 入力できるが壊れる状態を本番に出すことになる |
| 「テストは次のスプリントで」 | 完了の定義を割ることになる。サイズは減らず、負債が増えるだけ |
| 「顧客側だけ作って店側は後で」 | 買取のように**両側揃って初めて回る**業務では、価値がゼロのまま止まる |

## 5. スプリントへの割り当て

**大きさを揃えただけでは、スプリントは安定しない。** 3〜4 個の PBI が全部
一本の鎖でつながっていれば、先頭が詰まった瞬間に全部が落ちる。

| # | 規則 |
| --- | --- |
| F1 | **同一スプリント内の依存の鎖は 3 段まで。** 4 段以上を作らない |
| F2 | **各スプリントに、独立に着手できる PBI を 2 件以上**置く。1 件しか無いスプリントは、先頭が詰まるとチームの大半が遊ぶ |
| F3 | 業務そのものが直列な区間（この店では買取）では、**依存の無い PBI を他のリリースから 1 件借りてくる**。借りるのは、そのリリースで**先に要る**ものに限る |
| F4 | 投入は容量の 100 % を上限とし、**不確実性の高い区間ほど落とす**。落とす順は「公開直後 → 新しいサブドメイン → 通常」 |
| F5 | 合意 PBI とそれを使う実装 PBI を**同一スプリントに置くのは、合意が半日で終わる見込みのときだけ**。PO の判断が要るものは 1 スプリント前へ出す |

F1・F2 は機械的に検査できる。**バックログを並べ替えたら必ず検査する。**

### 5.1 リリース最終スプリントの扱い

リリースの最終スプリントは、通しの手動テスト・配備・受け入れに時間を取られる。
**届ける相手が広いほど、その分を大きく空ける。**

| 届ける相手 | 空ける量の目安 |
| --- | --- |
| チームだけ | 空けない |
| 店舗スタッフ（内部） | 容量の 1 割 |
| 市場（MVP 以降） | 容量の 3〜4 割 |
