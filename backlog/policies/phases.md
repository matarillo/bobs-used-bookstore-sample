# 開発フェーズ

PBI の割り方と受け入れ基準の書き方は、**開発の局面によって変わる**。
変えてよいのではなく、変えないと成立しない。局面を三つに分け、
それぞれの終わりを**判定できる形**で定める。

## 1. なぜ局面で変えるのか

初期に不確かなのは「何を作るか」ではなく **「どう作るか」** である。
ドメインモデルもアーキテクチャも物理設計（どの csproj のどの名前空間に何を置くか）も
決まっていない。この状態で「要求から実装・テストまで」を 1 つの PBI に収めると、
見積りの大半が**まだ存在しない決定**に対する当て推量になり、規模は XL・XXL へ膨らむ。

膨らんだ PBI はスプリントを跨ぐ。跨いだ PBI は「終わったこと」を数えられなくする。
数えられないとベロシティが立たず、リリースのリズムが読めなくなる。

だから初期は **決定を作る PBI と、決定に従う PBI に割る**。
決定が積み上がって型になれば、割る必要はなくなる。

## 2. 三つの局面

| 局面 | 何が不確かか | PBI の主な種別 | 目安 |
| --- | --- | --- | --- |
| **初期** — 形を決める | どう作るか。集約境界・層・置き場・テストの型 | 合意 / 基盤 / 実装 | R0 〜 R1 |
| **中期** — リズムに乗る | 何を作るか。細部の業務判断 | 実装（合意を内包） | R1 後半 〜 R3 |
| **後期** — 広げて締める | どれだけの品質で足りるか。運用と数字 | 実装（非機能・運用） | R4 以降 |

局面はカレンダーではなく**状態**である。下の判定条件を満たすまで、初期は終わらない。

## 3. 初期 → 中期の判定条件

次の四つが **2 スプリント連続で変わらなかった**ら中期に入る。

1. **集約マップ**（[domain/overview.md](../../docs/design/domain/overview.md) の `AGG-` と整合性境界）
2. **物理設計の規約** — csproj・名前空間・クラスの置き場・テストの置き場
3. **`UC-` の書式と BCE の切り方** — Boundary / Controller / Entity に何を書くかで迷わない
4. **テストの層と粒度** — どこを自動で固定し、どこを手で確かめるか

**「変わらなかった」は、変更が起きなかったことではない。**
変更が起きても、**既にある規約の中で吸収できた**なら変わっていない。
規約そのものを書き換えたら、そのスプリントは数え直しである。

判定は スプリントレビューの直後に、チームで 5 分で行う。

## 4. 中期 → 後期の判定条件

次のいずれも満たしたら後期に入る。

1. すべての `EPIC-` の **コア価値**が届き終わっている（付加価値は残っていてよい）
2. 残るバックログの**過半**が、付加価値・非機能・運用の PBI である
3. 「規定しない」と決めた `NFR-`（[non-functional.md §3.2](../../docs/spec/non-functional.md)）のうち、
   **実運用の数字が要求し始めたもの**が現れている

3 が現れないうちに後期の作り込みを始めるのは、要らない品質を買うことである。

## 5. 局面が後戻りすることがある

新しいサブドメインに入るとき（この店では **買取＝ R3**）、集約もルールも新しく、
最も危うい仮説（[HYP-05](../../docs/product/hypotheses.md)）を抱えている。
中期にいても、そのストーリー群に限って**初期のやり方に戻す**——
合意 PBI を分けて先に置く。

判定条件: 次のいずれかに当てはまるストーリー群は、局面によらず合意 PBI を分ける。

- 状態 **仮説** または **検証中** の `HYP-` に依存している
- 優先度 **A** の `Q-` が未回答のまま含まれている
- 既存の `AGG-` に無い新しい集約を必要とする

この店では `PBI-030`（買取の成立の仕方を決める）がこれに当たる。
