# 受け入れ基準の記述指針

**何を書き、どの粒度で書くか**を局面ごとに定める。
局面の定義は [phases.md](phases.md)、PBI の割り方は [splitting.md](splitting.md) にある。

## 0. すべての局面に共通する規則

| # | 規則 |
| --- | --- |
| G1 | **観測できることを書く。** 「〜を実装する」「〜を考慮する」は基準ではない |
| G2 | **本文も値も写さない。** 業務ルールは `RULE-`、品質水準は `NFR-`、画面の項目は `UC-` の Boundary を**識別子で参照**する（[文書体系 §6.1](../../docs/README.md)） |
| G2a | **とりわけ数値を書かない。** 「≦ 5 冊」「7 日後」「税率 10 %」は、それを**決める合意 PBI の成果**である。受け入れ基準に書いた瞬間、その PBI は「決める」ではなく「決まった答えを写す」作業になる |
| G3 | **各基準に確かめ方を付す。** `（自動）` `（手動）` `（読み合わせ）` のいずれか |
| G4 | **満たせなかったことも成果になりうる。** 「決まらなかった」を `Q-` に、「守れなかった」を `ISSUE-` に落とせたなら、それは完了である |

G2 を破ると、税率を変えたときに直す場所がバックログにも増える。
バックログは**製品の記述ではない**（[README §1](../README.md)）。

## 1. 開発初期 — 合意 PBI の受け入れ基準

### 1.1 何を書くか

**「文書が書けた」ではなく「決まった／決まっていないことが確定した」を書く。**

| 書く | 書かない |
| --- | --- |
| どの識別子（`UC-` `RULE-` `AGG-` `INV-`）が起票・更新されたか | 文書の行数・章立て |
| **誰と**読み合わせ、**何に言質が取れたか** | 「レビューを実施した」 |
| 未決が `Q-` として残り、優先度と再訪条件が付いたこと | 「課題を洗い出した」 |
| `[強制]` にできなかった不変条件が `ISSUE-` を持つこと | 実装での対処方法 |
| `SCR-` のワイヤーフレームを**ブラウザで読み合わせ**、版面に合意したこと | 画面の実装、配色、部品の実現方式 |
| **次の実装 PBI が着手できる状態になったこと** | 実装の完成 |

### 1.2 記述レベル

- **粒度**: 1 つの `UC-` グループ、または 1 つの横断的作法につき 4〜6 項目。
- **主語**: 「顧客 PO が」「チームが」。システムではない。
- **判定**: **その場で ○ × が付く**こと。「十分に議論した」は判定できない。
  「この画面で棚は作れる、と PO が言った」は判定できる。
- **禁止**: 画面の見た目、クラス名、コードの完成を条件に入れない。
  合意 PBI が実装の完了を待つと、割った意味が消える。

### 1.3 型

```markdown
- [ ] 棚に本を載せる操作を UC- として書き起こし、採番した。その Boundary
      （入力項目・操作・表示）を顧客 PO と読み合わせ、「この項目と操作で棚は作れる」と
      言質が取れている（読み合わせ）
- [ ] 上記に要る業務ルールを RULE- として採番し、**顧客が決めた値が入っている**
      （在庫の下限、原価の扱い）（読み合わせ）
- [ ] 対応する SCR- のワイヤーフレームを描き、ブラウザで読み合わせて版面に合意した
      （読み合わせ）
- [ ] 書籍の集約を AGG- として起こし、属性と不変条件をチームと AI で突き合わせた。
      [強制] にできないものが ISSUE- を持っている（読み合わせ）
- [ ] 関係する Q- が「回答」か「残置」に仕分けされ、残置には ADR- と再訪条件がある
      （読み合わせ）
- [ ] 決まらなかった事項が「ドメイン未定義」と明記されている（読み合わせ）
```

**値を書かず、値が入ったことを書く。** 「在庫僅少は 5 冊以下」と書けば、
それは決める作業ではなく写す作業になる。「`RULE-` に顧客が決めた値が入っている」と書けば、
決めるのは PO であり、基準は決まったことだけを判定する。

### 1.4 よくある誤り

| 誤り | なぜ誤りか | 直し方 |
| --- | --- | --- |
| 「仕様書を書く」 | 書けたかどうかしか判定できない | 「読み合わせて言質が取れている」に変える |
| 「すべての `Q-` を解消する」 | 解消できない `Q-` があるのが正常である（見送りは `Q-` を消費しない／[文書体系 §6.3](../../docs/README.md)） | 「回答か残置に**仕分けされている**」に変える |
| 「設計を確定する」 | 確定しない。初期に確定を条件にすると永遠に終わらない | 「次の実装 PBI が着手できる」に変える |
| 決まった値・状態遷移・集約名を基準に書く | PO が別の答えを出した瞬間に満たせない基準になる。**答えを知っている人間にしか書けない** | 「何が決まったか」を書く。答えそのものは `RULE-`／`design/` に置く |
| 合意 PBI に**画面の実装**を求める | 実装の待ちが入る | 合意するのは版面までである。動く画面は実装 PBI の成果である |

## 2. 開発初期 — 実装 PBI の受け入れ基準

### 2.1 何を書くか

**振る舞い + 型が守られていること**の二本立てにする。

初期の実装 PBI は、機能を届けると同時に**物理設計の型を作る／型に従う**。
だから、この局面**だけ**は設計上の約束を受け入れ基準に書いてよい
（[splitting.md B5](splitting.md)）。中期に入ったら書かない。

| 書く | 書かない |
| --- | --- |
| ユーザーが観測できる振る舞い（`UC-` 参照つき） | 計算式・しきい値の本文（`RULE-` を参照する） |
| **層の規約が守られていること**（例: 業務上の条件分岐が Controller にない） | **クラス名・メソッド名**。規約であって実装ではない |
| 増えた自動テストがどの `SPEC-` に入るか | テストの本数 |
| 異常系が 1 つ以上 | すべての異常系（初期は代表 1 つでよい） |

### 2.2 記述レベル

- **粒度**: 1 PBI につき 4〜6 項目。うち **1 項目は異常系**、**1 項目は型の遵守**。
- **設計制約の書き方**: 「`Bookstore.Domain` の `Book` クラスに `AddStock` を作る」ではなく
  「在庫超過の判定が**ドメイン層にあり**、Controller に条件分岐がない」と書く。
  前者はコードレビューの話、後者は[アーキテクチャの約束](../../docs/design/architecture.md)である。
- **デモ**: 「スプリントレビューで**この操作をこの順にやって見せられる**」を最後の 1 項目に置く。

### 2.3 型

```markdown
- [ ] [UC-STAFF-14] 書名・著者・ISBN・分類・売価・在庫数を入力して登録すると、
      在庫一覧に現れる（自動）
- [ ] [RULE-BOOK-01] 仕入原価を入れなければ粗利見込は「未定義」と表示され、
      0 とは表示されない（自動）
- [ ] [異常系] 必須項目が欠けた状態で登録すると、その場に理由が出て入力内容が
      失われない（手動）
- [ ] [NFR-SEC-03] Administrators 以外はこの画面に到達できない（自動）
- [ ] [型] AGG-BOOK の生成がドメイン層にあり、Controller に業務上の条件分岐がない
      （読み合わせ）
- [ ] スプリントレビューで「登録 → 一覧に出る」を実演できる（手動）
```

## 3. 開発中期 — 受け入れ基準

### 3.1 何を書くか

**ユーザーが観測できる振る舞いだけを書く。** 設計の約束は基準から降ろす。

型は既に決まっており、守られているかはコードレビューと静的検査が見る。
受け入れ基準に残し続けると、PO が読めない基準が増え、受け入れの場が設計レビューに変質する。

| 書く | 書かない |
| --- | --- |
| Given / When / Then で言える振る舞い | 層・クラス・置き場 |
| **異常系を必ず 1 つ以上**（同時操作・権限・状態違反） | 網羅的な異常系一覧（`UC-` の異常系節が正） |
| 参照する `UC-` / `RULE-` / `NFR-` の識別子 | それらの本文 |
| 確かめ方（自動 / 手動） | テストの実装方法 |

### 3.2 記述レベル

- **粒度**: 1 PBI につき **4〜7 項目**。増えるなら PBI が大きい。
- **書式**: 1 項目 = 1 文。前半に `[識別子]`、後半に観測できる事実。
- **境目**: 「PO が読んで、○ か × かを自分で判定できるか」。できなければ書き直す。
- **異常系の選び方**: `UC-` の異常系節のうち、**現場が日常的に踏むもの**を挙げる
  （[Q-07](../../docs/product/open-questions.md) が言う「同時操作の競合」がこれに当たる）。

### 3.3 型

```markdown
- [ ] [UC-CUST-20] 受付待ち・受付済の注文を取り消すと、状態が取消済になり、
      各明細の数量が在庫に戻る（自動 / SPEC-ORDER）
- [ ] [RULE-SERVICE-05] 取消済の注文をもう一度取り消しても、画面はエラーにならない（自動）
- [ ] [UC-CUST-20 異常系] 出荷済の注文には取消の操作が出ない（手動）
- [ ] [RULE-ACCESS-01] 他人の注文番号を指定しても取り消せず、その旨が伝わる（自動）
- [ ] [conventions] 取消の前に確認を挟み、成功したことが画面で分かる（手動）
```

### 3.4 中期で基準が膨らむときの合図

| 合図 | 意味 | 手当て |
| --- | --- | --- |
| 項目が 8 個を超える | PBI が 2 つ分ある | `UC-` 単位で割る |
| 「〜も」「かつ」が増える | 1 項目に 2 つのことを書いている | 分ける |
| 設計の言葉が戻ってくる | 型が揺れている。局面が初期に戻っている | [phases.md §5](phases.md) を確認する |

## 4. 開発後期 — 受け入れ基準

### 4.1 何を書くか

**数値と、その測り方をセットで書く。** 機能の受け入れとは基準の性格が変わる。

| 書く | 書かない |
| --- | --- |
| **状況 → 応答 → 測定**（`NFR-` と同じ書式／[non-functional.md §2](../../docs/spec/non-functional.md)） | 「速い」「落ちない」「安全」 |
| **既存の振る舞いを壊していないこと**（回帰）を明示的に 1 項目 | 「デグレなきこと」（判定できない） |
| 運用手順は**実演した事実**（誰が立ち会い、何分で戻ったか） | 手順書の完成 |
| 判断の材料が取れること（`HYP-` / `RISK-` の**監視列が埋まる**） | 指標の解釈 |
| 昇格した `NFR-` が `[強制]` なら、それを固定する**自動テストがあること** | — |

### 4.2 記述レベル

- **粒度**: 1 PBI = 1 つの `NFR-` または 1 つの運用手順。項目は 3〜5。
- **数値の出どころ**: 思いつきの数値を書かない。
  **測ってから決める**か、[tradeoffs](../../docs/product/tradeoffs.md) の品質バーから引く。
  測っていない数値を `[強制]` にすると、達成できない基準が残る。
- **回帰の書き方**: 「`SPEC-ORDER` と `SPEC-OFFER` の自動テストが全て通る」のように、
  **固定されている範囲の識別子**で書く。
- **`[規定しない]` からの昇格**: 「規定しないままでよい」と決まることも合格である。
  そのときは `ADR-` と再訪条件を残す。

### 4.3 型

```markdown
- [ ] [NFR-DATA-01] 障害発生時、直近 24 時間以内の任意の時点へ復旧できる。
      復旧の実演を PO 立ち会いで 1 回行い、所要時間を記録した（手動）
- [ ] [回帰] 復旧後のデータで SPEC-ORDER / SPEC-OFFER の自動テストが全て通る（自動）
- [ ] [RISK-06] risks.md の監視列が「バックアップ成否の日次確認」に置き換わっている
      （読み合わせ）
- [ ] [強制] バックアップが無効化されたら検知できる自動テストまたは監査項目がある（自動）
```

## 5. 三つの局面の比較

| 観点 | 初期（合意） | 初期（実装） | 中期 | 後期 |
| --- | --- | --- | --- | --- |
| 主語 | 顧客 PO / チーム | システム | システム | システム |
| 何を判定するか | **決まったか** | 動くか **+ 型に従ったか** | 動くか | **どれだけの品質で動くか** |
| 設計の言葉 | 論理設計まで可 | **型の遵守として可** | **書かない** | 書かない |
| 数値 | 不要 | 不要 | ルールの識別子で参照 | **必須。測り方とセット** |
| ワイヤーフレーム | **描いて版面に合意する** | 版面どおりに実装されたか | 差分のある画面だけ描き直す | 描き直さない |
| 異常系 | — | 代表 1 つ | **必ず 1 つ以上** | 回帰として全体 |
| 項目数 | 4〜6 | 4〜6 | 4〜7 | 3〜5 |
| 受け入れる人 | PO（仕様）/ チーム（設計） | PO | PO | PO + 運用担当 |
| 「未決が残った」の扱い | **成果**（`Q-` に落ちていれば合格） | `ISSUE-` に落ちていれば合格 | 同左 | 同左 |
