# 顧客：本を売る

対象画面: `SCR-RESALE`, `SCR-RESALE-NEW`
**ログインが必要**である。

> ここは**買取 (Buying)** の流れの入口である。以降の審査・支払・棚入れはスタッフ側
> （[ユースケース](staff-offers.md), [ユースケース](staff-catalog.md)）へ続く。
> 顧客から見た全体像は [docs 02 §7.1](../../design/domain/overview.md) を参照。

## UC-CUST-21 — 買取を申し込む

| 項目 | 内容 |
| --- | --- |
| アクター | 顧客 |
| 画面 | `SCR-RESALE-NEW` |
| ドメイン対応 | [OP-CUST-14](../../design/domain/operations.md) |
| 目的 | 手持ちの本を店に買い取ってもらえるか打診する |

**【Boundary：画面】**

- 入力項目:

  | 項目 | 必須 | 入力の形 |
  | --- | --- | --- |
  | 書名 | ● | 自由入力 |
  | 著者 | ● | 自由入力 |
  | ISBN | ● | 自由入力 |
  | 出版社 | ● | 選択（参照データから） |
  | 書籍種別 | ● | 選択（参照データから） |
  | ジャンル | ● | 選択（参照データから） |
  | 状態（コンディション） | ● | 選択（参照データから） |
  | 希望買取価格 | ● | 金額。**0 以上 1,000,000 以下** |

- 操作: 「保存」
- 成功時: `SCR-RESALE` へ移る。**通知バナーは出ない**（一覧に自分の申込が増えていることで分かる）
- 失敗時: この画面に留まり、項目ごとにメッセージを出す。**選択肢と入力内容は保たれる**
- **本の状態を写真で伝える手段はない**（表紙画像は店が棚入れ時に用意する）
- **概要・備考を書く欄はない**

**【Controller：手順】**

1. 参照データ（出版社・書籍種別・ジャンル・状態）を取得し、選択肢として画面に渡す。
2. 入力を検証する。不備があれば選択肢を用意し直してこの画面を描く。
3. 主体識別子とともに、買取オファーの申込を依頼する。
4. 単位作業を完了する。
5. `SCR-RESALE` へ遷移する。

**【Entity：ルール】**

- `AGG-OFFER`: [INV-OFFER-01](../../design/domain/invariants.md)（顧客・書誌・分類・買取価格が必ず要る）、[INV-OFFER-02](../../design/domain/invariants.md)（生成直後は**承認待ち**）、[INV-OFFER-08](../../design/domain/invariants.md)（買取価格は 0 以上）
- [INV-CLASS-01](../../design/domain/invariants.md): 分類の 4 軸は、**その位置が要求する種別の実在する項目**でなければならない（例：ジャンル欄に出版社を指定できない）
- [RULE-TRADE-03](../rules.md): **売価は買取価格から導出されない。** 店が独立に決める
- **買取価格の算定基準はドメインに存在しない**（[docs 12 §4](../../design/domain/invariants.md)）。値付けは顧客の申告に委ねられている
- `RULE-UI-08`（**ドメイン未定義**）: 希望買取価格の上限を 1,000,000 とする。
  → *【問い】* 上限・下限は業務としてどうあるべきか。**0 円での申込が通る**が意図した動作か（[Q-20](../../product/open-questions.md)）
- **顧客が存在するかを確認していない**（[ISSUE-04](../../design/issues.md)）。
  実際にはログイン時に顧客が作られるため問題は表面化しない

**【異常系】**

| 起きること | 画面の振る舞い |
| --- | --- |
| 必須項目が空／価格が範囲外 | この画面に留まり、項目ごとにメッセージ |
| 選択した分類の項目が実在しない | 失敗し、エラー画面へ落ちる（[Q-07](../../product/open-questions.md)） |
| 同じ本を二重に申し込んだ | **重複を検査しない。** 2 件の申込として並ぶ |

## UC-CUST-22 — 自分の買取申込を一覧する

| 項目 | 内容 |
| --- | --- |
| アクター | 顧客 |
| 画面 | `SCR-RESALE` |
| ドメイン対応 | [OP-CUST-15](../../design/domain/operations.md) / [RM-OFFER-BY-CUSTOMER](../../design/domain/read-models.md) |
| 目的 | 出した申込がどうなったかを知る |

**【Boundary：画面】**

- 表示項目（申込ごと）: 書名、著者、ジャンル、出版社、書籍種別、ISBN、状態（コンディション）、買取価格、**申込の状態**
- 申込の状態: 承認待ち／承認済（発送待ち）／受領確認済／支払完了／却下／棚入れ済
- 操作: 「買取を申し込む」（→ `SCR-RESALE-NEW`）のみ
- **申込ごとの操作は一つもない**。取り下げも修正もできない
- **申込日・支払日は表示していない**
- ページ送り・絞り込みなし

**【Controller：手順】**

1. 主体識別子で自分の買取申込を取得する。
2. `SCR-RESALE` に渡して描画する。

**【Entity：ルール】**

- `AGG-OFFER`: 状態の語彙は [01-ubiquitous-language §6.2](../../glossary.md) を用いる
- [RULE-ACCESS-01](../rules.md): 本人の申込だけが見える
- **顧客側からの取り下げ操作はドメインに存在しない**（[docs 11 §4](../../design/domain/operations.md)）

> **業務上もっとも重要な欠落**: 申込が「承認済（発送待ち）」になったとき、
> **顧客は本を店に送らなければならない**。しかしこの画面は状態を表示するだけで、
> 「本を送ってください」とも「どこへ送るか」とも言わない。通知も届かない。
> 買取の流れが顧客側で止まる原因になる（[Q-21](../../product/open-questions.md)）。

**【異常系】**

| 起きること | 画面の振る舞い |
| --- | --- |
| 却下された | 状態が「却下」になるだけ。**理由は伝えられない**（[Q-21](../../product/open-questions.md)） |
| 支払われた | 状態が「支払完了」になるだけ。**支払日も支払方法も表示されない** |
| 申込が 0 件 | 空の表を描く（[Q-12](../../product/open-questions.md)） |
