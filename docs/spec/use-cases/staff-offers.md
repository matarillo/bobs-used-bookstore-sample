# スタッフ：買取オファーを裁く

対象画面: `SCR-A-OFFERS`
**管理者グループに属していること**が条件。

> この画面は**買取の流れそのもの**である。顧客の申込から、店が代金を払うまでの全段階が
> 1 つの一覧の上で進む。棚入れ（在庫にする）だけが別画面へ移る（[ユースケース](staff-catalog.md) §3）。
> 状態遷移の全体像は [docs 12 §3.2](../../design/domain/invariants.md) を参照。

## UC-STAFF-07 — 買取オファーを一覧・絞り込む

| 項目 | 内容 |
| --- | --- |
| アクター | 店舗スタッフ |
| 画面 | `SCR-A-OFFERS` |
| ドメイン対応 | [OP-STAFF-11](../../design/domain/operations.md) / [RM-OFFER-LIST](../../design/domain/read-models.md) |
| 目的 | 今どの申込に手を打つべきかを見つける |

**【Boundary：画面】**

- 絞り込み条件: 書名、著者、ジャンル、状態（コンディション）、**申込の状態**。「絞り込む」「解除」
- 表示項目（申込ごと）: **顧客名**、書名、著者、ジャンル、コンディション、買取価格、申込日、状態、操作
- ページ送りあり（[横断的な約束事](../conventions.md) §3）
- **操作は状態によって出し分ける**（下表）。これはワイヤーフレームで描き分けること

  | 申込の状態 | 出る操作 |
  | --- | --- |
  | 承認待ち | 「承認」「却下」 |
  | 承認済（発送待ち） | 「発送を確認」 |
  | 受領確認済 | 「支払う」 |
  | 支払完了・未棚入れ | 「在庫に追加」（→ `SCR-A-BOOK-EDIT` 棚入れモード） |
  | 支払完了・棚入れ済 | 操作なし。「在庫済」と表示 |
  | 却下 | 操作なし |

**【Controller：手順】**

1. 絞り込み条件と頁番号を受け取る。
2. 条件に合うオファーの頁を問い合わせる。
3. 参照データ（ジャンル・コンディション）を取得し、絞り込みの選択肢として渡す。
4. `SCR-A-OFFERS` に渡して描画する。

**【Entity：ルール】**

- `AGG-OFFER`: 状態ごとに次に取りうる遷移は集約が定める（[INV-OFFER-03〜06](../../design/domain/invariants.md)）。
  **画面の出し分けは、この遷移可能性を写したものである**（画面が独自に判断しているのではない）
- [RULE-ACCESS-02](../rules.md): 絞り込みなしの照会はスタッフ専用
- `RULE-UI-09`（**ドメイン未定義**）: 操作の名称が用語集と食い違う。
  「発送を確認」は、業務上は**店が現物を受け取った**ことを記録する操作（受領確認済）である。
  → *【問い】* ラベルを用語集（[01-ubiquitous-language §6.2](../../glossary.md)）に合わせるか、用語集を現場の言い方に合わせるか（[Q-22](../../product/open-questions.md)）

**【異常系】**

| 起きること | 画面の振る舞い |
| --- | --- |
| 絞り込んだあと | **条件が入力欄に残らない**。結果は正しく絞られる（[Q-10](../../product/open-questions.md)） |
| 申込日の絞り込み | **できない**。ダッシュボードから「今月の申込」を辿ると条件が効かない（[Q-10](../../product/open-questions.md)） |

## UC-STAFF-08〜11 — 買取オファーの審査と支払

4 つの操作は**同じ形**をしている。違いは遷移と副作用だけである。

| # | ユースケース | 操作名（画面） | 遷移元 | 遷移先 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| `UC-STAFF-08` | 承認する | 「承認」 | 承認待ち | 承認済 | — |
| `UC-STAFF-09` | 却下する | 「却下」 | 承認待ち／受領確認済 | 却下 | — |
| `UC-STAFF-10` | 受領を確認する | 「発送を確認」 | 承認済 | 受領確認済 | — |
| `UC-STAFF-11` | 支払を記録する | 「支払う」 | 受領確認済 | 支払完了 | **支払日を記録する** |

| 項目 | 内容 |
| --- | --- |
| アクター | 店舗スタッフ |
| 画面 | `SCR-A-OFFERS` |
| ドメイン対応 | [OP-STAFF-06〜09](../../design/domain/operations.md) |
| 目的 | 買い取るか断るかを決め、現物を受け取り、代金を払う |

**【Boundary：画面】**

- 操作: 一覧の行にあるボタン。**確認ダイアログはない**
- フィードバック: `SCR-A-OFFERS` に戻り、通知バナー（「承認しました」「却下しました」「本を受け取りました」「支払いました」）
- 行の状態表示と操作ボタンが、遷移先のものに入れ替わる

**【Controller：手順】**

1. 対象のオファー識別子を受け取る。
2. **オファーに状態遷移を依頼する**（遷移できるかどうかの判断は集約が行う。手順側では判断しない）。
3. 更新日時を記録する。
4. 単位作業を完了する。
5. `SCR-A-OFFERS` へ戻し、通知バナーを出す。

**【Entity：ルール】**

- `AGG-OFFER`: [INV-OFFER-03](../../design/domain/invariants.md)（**承認待ち → 承認済 → 受領確認済 → 支払完了 の順にのみ進む**）
- `AGG-OFFER`: [INV-OFFER-04](../../design/domain/invariants.md)（却下は承認待ちまたは受領確認済からのみ）、[INV-OFFER-10](../../design/domain/invariants.md)（却下されたオファーは支払われず、棚入れもされない）
- `AGG-OFFER`: [INV-OFFER-05](../../design/domain/invariants.md)（**支払は受領確認済からのみ。支払日が同時に記録される**）
- [RULE-PERIOD-05](../rules.md): 買取の支出は**支払日**で期間に割り当てられる。申込日ではない（ダッシュボードの数字に直結する）
- [INV-OFFER-11](../../design/domain/invariants.md) は **[不成立]**: 支払後に買取価格が変わらないことをモデルが保証していない。
  画面から変える手段はないため、現状は表面化しない

> **支払の記録は「支払った」という事実の記録であって、支払そのものではない。**
> 実際の送金手段はこのシステムの外にある。支払方法・支払先を記録する項目もない
> （[Q-28](../../product/open-questions.md)）。

**【異常系】**

| 起きること | 画面の振る舞い |
| --- | --- |
| 遷移できない状態のオファーを操作した（二重クリック、別のスタッフが先に処理した） | **失敗し、エラー画面へ落ちる**。何が起きたかは伝わらない（[Q-07](../../product/open-questions.md)） |
| 却下したあとで撤回したい | **できない。** 却下からの遷移は存在しない |
| 承認したあと、いつまでも本が届かない | **画面上で追跡する手段がない。** 「承認済のまま何日経過したか」を測る指標も導線もない（[Q-21](../../product/open-questions.md)） |

## 買取から販売への接点

支払完了のオファーだけが**棚入れ**（在庫にする）へ進める。
これが買取と販売をつなぐ**唯一の接点**である（[docs 02 §2](../../design/domain/overview.md)）。

- [RULE-TRADE-01](../rules.md): **店は買っていない本を売らない**（棚入れは支払完了を要求する）
- [RULE-TRADE-02](../rules.md): 1 件の申込は 1 冊の書籍になる。**二重の棚入れは拒否される**

棚入れの操作そのものは [UC-STAFF-16](staff-catalog.md#uc-staff-16--支払済のオファーを棚入れする) に記述する。
