# 非機能仕様（Non-Functional Requirements）

機能が「何ができるか」なら、ここは **「どれだけの品質でできるか」** を定める。
外から観測でき、テストできる品質水準を `NFR-` として採番する。
テスト可能な粒度であることが、顧客と合意できることの条件である（[文書体系 §1.2](../README.md)）。

## 1. 品質はプロダクトごとに決める — 過剰も不足も避ける

どれだけの品質が要るかは開発手法ではなく、**誰がどう使うか**で決まる。
銀行の振込と使い捨てキャンペーンでは要求水準がまるで違う。

早期・小規模なら全観点を埋めない。**要るものだけを `NFR-` にし、残りは「規定しない」と明記して、
プロダクトの成長に応じて育てる**（規定がないことも仕様である／[文書体系 §9](../README.md)）。
どの品質を [強制] にするかは、[トレードオフの品質バー](../product/tradeoffs.md) が決める。

## 2. 記述形式 — 品質シナリオ

各 `NFR-` は、状況・応答・測定の三つで、テストできる形に書く。
「速いこと」ではなく「通常時、検索が p95 で N ms 以内」と書く。

| 項目 | 内容 |
| --- | --- |
| **状況** | いつ・何が起きたとき（負荷、外部障害、攻撃、通常操作…） |
| **応答** | システムは観測可能に、どう応じるか |
| **測定** | 何を満たせば合格か（数値・判定条件） |
| **強制** | `[強制]` 必達 / `[目安]` 努力目標 / `[規定しない]` 今は問わない |
| **由来** | `RISK-` / `HYP-` / `constraints` / `tradeoffs` |

## 3. 観点の一覧（チェックリスト）

要否を 1 つずつ判断する。要るものは `NFR-` を起こし、要らないものは「規定しない」と記す。
**この一覧は網羅ではない。** プロダクトに関係ない観点は挙げなくてよい。

- **可用性** — 稼働率、障害時の縮退、復旧（外部が落ちたときの見せ方など）
- **性能** — 応答時間、スループット、同時実行
- **セキュリティ** — 認証認可、データ秘匿、入力の防御
- **運用・保守性** — 監視、バックアップ、計画停止の見せ方
- **データ・移行** — 保持期間、移行時の振る舞い、整合
- **互換・環境** — 対応ブラウザ／端末、適合規格
- **アクセシビリティ** — 到達可能性の水準
- **多言語** — 文言の外部化、切替

## 4. 台帳

| ID | 観点 | 状況 → 応答 → 測定 | 強制 | 由来 |
| --- | --- | --- | --- | --- |
| NFR-PERF-01 | 性能 | 通常時、書籍検索 → 結果を返す → p95 < {N} ms | [目安] | constraints |
| NFR-AVAIL-01 | 可用性 | 決済外部が応答しないとき → 注文を確定させない・かごを保持 → 注文喪失ゼロ | [強制] | RISK-…, EXT-PAYMENT |
| NFR-SEC-01 | セキュリティ | 個人情報を扱うとき → 保存時・通信時に暗号化 → 構成監査で確認 | [強制] | RISK-… |
| NFR-A11Y-01 | アクセシビリティ | 主要導線を操作するとき → 支援技術で到達可能 → 監査で AA | [目安] | constraints |

## 5. テストで固定する

`[強制]` の `NFR-` は、設計層のテスト（`SPEC-`）で検証されるべきである。
検証されていない `[強制]` は、`design/issues.md` に対応する `ISSUE-` を持つ
（[強制] を掲げて検証していない状態を放置しない）。
