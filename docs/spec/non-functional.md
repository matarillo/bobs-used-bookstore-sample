# 非機能仕様（Non-Functional Requirements）

機能が「何ができるか」なら、ここは **「どれだけの品質でできるか」** を定める。
外から観測でき、テストできる品質水準を `NFR-` として採番する。
テスト可能な粒度であることが、顧客と合意できることの条件である（[文書体系 §1.2](../README.md)）。

## 1. 品質はプロダクトごとに決める — 過剰も不足も避ける

どれだけの品質が要るかは開発手法ではなく、**誰がどう使うか**で決まる。
銀行の振込と使い捨てキャンペーンでは要求水準がまるで違う。

この店の判断は明快である。**守るのは「取引と個人情報の正しさ・安全」だけであり、
性能・可用性・アクセシビリティは現段階では規定しない。**
小規模な単一店舗の EC であり、コスト上限（[constraints](../product/constraints.md)）が品質の上限を規定する。
どの品質を [強制] にするかは、[トレードオフの品質バー](../product/tradeoffs.md) が決める。

## 2. 記述形式 — 品質シナリオ

各 `NFR-` は、状況・応答・測定の三つで、テストできる形に書く。
「速いこと」ではなく「通常時、検索が p95 で N ms 以内」と書く。

| 項目 | 内容 |
| --- | --- |
| **状況** | いつ・何が起きたとき（負荷、外部障害、攻撃、通常操作…） |
| **応答** | システムは観測可能に、どう応じるか |
| **測定** | 何を満たせば合格か（数値・判定条件） |
| **強制** | `[強制]` 必達 / `[目安]` 努力目標 / `[規定しない]` 今は問わない |
| **由来** | `RISK-` / `HYP-` / `constraints` / `tradeoffs` |

## 3. 台帳

### 3.1 セキュリティ — この店が守ると決めた品質

| ID | 状況 → 応答 → 測定 | 強制 | 由来 |
| --- | --- | --- | --- |
| NFR-SEC-01 | 平文 HTTP でアクセスされた → HTTPS へ誘導し、以後の通信をすべて暗号化する（本番では HSTS を付す） → 平文のまま完結する応答が存在しないこと | [強制] | [品質バー](../product/tradeoffs.md) |
| NFR-SEC-02 | 未認証の利用者が画面を要求した → 匿名を明示的に許した画面（トップ・プライバシー・検索・書籍詳細・かご・欲しい物・エラー・ログイン操作）以外はログインへ誘導する → 画面一覧（[screens.md](screens.md)）との突き合わせで、匿名到達可能な画面が上記に限られること | [強制] | [conventions §6](conventions.md)、[RULE-ACCESS-01 / 02](rules.md) |
| NFR-SEC-03 | 管理者グループに属さない利用者が管理ポータルを要求した → 拒否する → `Administrators` 以外での管理画面到達が 0 であること | [強制] | [actors.md §1.1](../product/actors.md)、[RULE-ACCESS-02](rules.md) |
| NFR-SEC-04 | 画面を経ない偽造された更新要求（CSRF）が送られた → 拒否する → すべての更新系要求に検証が既定で適用されていること | [強制] | [品質バー](../product/tradeoffs.md) |
| NFR-SEC-05 | DB 資格情報を扱うとき → コード・リポジトリ・設定ファイルに置かず、秘匿情報の保管庫から実行時に取得する → 構成監査でリポジトリ内に資格情報が検出されないこと | [強制] | [EXT-CONFIG](integrations.md) |
| NFR-SEC-06 | 不適正な表紙画像が登録されようとした → 判定で拒否し、公開しない → [EXT-IMG-CHECK](integrations.md) の禁止カテゴリに該当する画像が配信されないこと | [強制] | [品質バー](../product/tradeoffs.md) |

### 3.2 規定しない観点

以下は**規定しない**。規定がないことも仕様である（[文書体系 §9](../README.md)）。
理由はコスト上限との交換であり、その受容は [risks.md](../product/risks.md) と
[constraints](../product/constraints.md) が持つ。プロダクトの成長に応じて `NFR-` に昇格させる。

| ID | 観点 | 規定しない内容と現状 |
| --- | --- | --- |
| NFR-PERF-01 | 性能 | 応答時間・スループットの水準を規定しない。想定規模（同時数十セッション——[constraints](../product/constraints.md)）では単一インスタンスで足りるという判断であり、実測もしていない |
| NFR-AVAIL-01 | 可用性 | 稼働率を規定しない。実行単位が 1 つであり（[architecture.md §7](../design/architecture.md)）、停止すれば店は閉まる。異常終了時の自動再起動のみ構成されている |
| NFR-DATA-01 | データ保護 | バックアップ・復旧目標を規定しない。**DB の自動バックアップは無効**であり、データ喪失は受容されている（[RISK-06](../product/risks.md)） |
| NFR-A11Y-01 | アクセシビリティ | 到達可能性の水準を規定しない |
| NFR-I18N-01 | 多言語 | 英語のみ。文言の外部化・切替を規定しない |
| NFR-COMPAT-01 | 互換・環境 | 対応ブラウザ・端末を規定しない |

## 4. テストで固定する

`[強制]` の `NFR-` は、設計層のテスト（`SPEC-`）で検証されるべきである。
検証されていない `[強制]` は、`design/issues.md` に対応する `ISSUE-` を持つ
（[強制] を掲げて検証していない状態を放置しない）。

**現状**: テストで固定されている範囲（[verified-by-test.md](../design/domain/verified-by-test.md)）は
ドメイン層に限られ、§3.1 の `[強制]` を固定する自動テストはまだない。
現時点の検証は実装構成の突き合わせ（本書の導出過程）によるものであり、
テストによる固定は未了である。対応する設計課題の採番は次の設計改訂で行う。
