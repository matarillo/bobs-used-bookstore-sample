# トレードオフと品質バー

不測の事態で、全部は守れない。**何を先に譲るか**を先に決めておくと、
チームも AI も、その場で迷わず・場当たりでなく判断できる。
これは顧客（プロダクトオーナー）が決める。

## 1. 何を先に譲るか（QCD+S）

品質(Q)・コスト(C)・納期(D)・スコープ(S)のうち、締め付けられたとき先に動かす順。
アジャイルの既定は **スコープを先に譲る**。

| 譲る順 | 項目 | この製品での方針 |
| --- | --- | --- |
| 1 | スコープ | まず削る。MVP 線の外から（[story-map.md §6](story-map.md)）。削ったものは `decisions/` に残す |
| 2 | 納期 | 次に送る。デリバリーは 2〜3 スプリントに 1 回の便であり（[story-map.md §6](story-map.md)）、間に合わないものは**次の便**に載せる。便自体は遅らせない |
| 3 | コスト | クラウド費用・人手の追加は店主の判断。月額上限は [constraints §3](constraints.md) が持つ |
| 4 | 品質 | 最後。ただし下の「譲らない品質」は動かさない |

## 2. 譲らない品質（品質バー）

ここに挙げた品質は、スコープや納期を犠牲にしても守る。
**これが [non-functional.md](../spec/non-functional.md) の `[強制]` NFR- を決める。**

- **金額が常に正しいこと。** 計算は非負・丸めを守り、成立した取引の金額
  （注文明細の価格・原価、支払済の買取価格）は後から変わらない
  （[VO-MONEY](../design/domain/building-blocks.md)、[RULE-MONEY-01](../spec/rules.md)。
  既知の逸脱は [ISSUE-07 / ISSUE-10](../design/issues.md) として追跡中）。
- **同じ 1 冊を二人に売らないこと。** 中古書店の在庫は通常 1 冊であり、二重販売は信用を直撃する。
  在庫の引き当ては注文の確定と同時に確定し、在庫を超える出庫は拒否される
  （[RULE-STOCK-01 / 03](../spec/rules.md)、
  [ISSUE-03](../design/issues.md) の意図的判断。ただし在庫数への直接代入がこの検査を迂回できる
  ——[ISSUE-01](../design/issues.md) として追跡中）。
- **本人のものしか見せない・触らせないこと。** 顧客向けの照会・操作は本人に限る
  （[RULE-ACCESS-01 / 02](../spec/rules.md)、[NFR-SEC-02 / 03](../spec/non-functional.md)）。
  ただし**注文確定時のかご・住所の所有者検証をドメインは保証していない**
  （[ISSUE-02](../design/issues.md)。防がれているとすればドメイン層の外である）。
- **通信と入力の基本的な防御。** 全通信の暗号化と CSRF 防御
  （[NFR-SEC-01 / 04](../spec/non-functional.md)）。

品質バーに入らない観点——性能・稼働率・バックアップ・アクセシビリティ・多言語——は、
[non-functional.md §3.2](../spec/non-functional.md) に **「規定しない」** と明記されている
（規定がないことも仕様である／[文書体系 §9](../README.md)）。

## 3. 育て方

早期に全部は決めない。**譲れない一線だけ**を先に置き、プロダクトの成長に応じて更新する。
方針を変えたら、理由を `decisions/` に残す（[文書体系 §6.2](../README.md)）。

買取（中核サブドメイン）の取引量が増えたら、真っ先に見直すのは
「バックアップを規定しない」（[NFR-DATA-01](../spec/non-functional.md)、[RISK-06](risks.md)）である。
支払の記録が失われると顧客との金銭トラブルに直結するためである。
