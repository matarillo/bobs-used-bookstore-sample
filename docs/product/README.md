# 要求・要件

**なぜこのシステムを作るのか**（要求）と、**そのうち何を引き受けるのか**（要件）を置く層である。

## 1. 目次

| 文書 | 層 | 内容 |
| --- | --- | --- |
| [goals.md](goals.md) | 要求 | 事業の循環と、店が測っている指標 |
| [actors.md](actors.md) | 要求 | 登場する人と、その人が達したいこと |
| [open-questions.md](open-questions.md) | 要求 | 業務担当者に確認しないと決められないこと `Q-` |

## 2. 要件はまだ形になっていない

引き受ける範囲を定めた文書は存在しない。
現在あるのは、**現行システムの姿から読み取った要求**と、**そこから出た未決事項**だけである。

要求と要件は、[open-questions.md](open-questions.md) の `Q-` に回答が出るのに従って形になる。
この層が薄いことは、現在の状態を正しく表している。

## 3. 決定が出たときの流れ

1. `product/decisions/` に決定を 1 ファイルとして記録する（`ADR-nnnn`）。
2. 業務ルールなら [spec/rules.md](../spec/rules.md) へ移す。`RULE-UI-` は識別子参照に置き換える。
3. 該当するユースケース・画面の記述を更新し、`status` を `agreed` にする。
4. [open-questions.md](open-questions.md) から当該 `Q-` を除く。

**決定の記録だけは理由を残す。** 同じ議論を繰り返さないためであり、経緯の記録ではない
（[文書体系 §6.2](../README.md)）。

## 4. 決定の記録の書式

```markdown
# ADR-0001 — （決めたことを一文で）

| 項目 | 内容 |
| --- | --- |
| 対象 | Q-nn |
| 決めた人 | |
| 影響する文書 | |

## 決めたこと
## そう決めた理由
## 採らなかった案とその理由
```
