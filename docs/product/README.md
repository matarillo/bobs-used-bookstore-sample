# 要求・要件

**なぜこのシステムを作るのか**（要求）と、**そのうち何を引き受けるのか**（要件）を置く層である。
この層は事実ではなく **仮説** から始まり、検証を通じて形になっていく。

## 1. 目次

| 文書 | 層 | 内容 |
| --- | --- | --- |
| [vision.md](vision.md) | 要求 | プロダクトの一文（価値提案）と非ゴール |
| [goals.md](goals.md) | 要求 | 事業の循環と、店が測っている指標 |
| [actors.md](actors.md) | 要求 | 登場する人と、その人が達したいこと |
| [hypotheses.md](hypotheses.md) | 要求 | 仮説 `HYP-` とその検証状態。要求を形にするエンジン |
| [story-map.md](story-map.md) | 要求 | ユーザーストーリー `STORY-` と MVP 線。`UC-` への橋 |
| [constraints.md](constraints.md) | 要求 | 前提と制約。テスト可能なものは `NFR-` へ |

## 2. 要求層は仮説から成る

引き受ける範囲を固定した要件文書は、まだ無い。
現在あるのは、現行システムから読み取った要求と、そこから出た未決事項、そして
**これから検証する仮説**である。

要求と要件は、[hypotheses.md](hypotheses.md) の `HYP-` が検証され、
[open-questions.md](open-questions.md) の `Q-` に回答が出るのに従って形になる。
この層に仮説が多く、確定した事実が少ないことは、現在の状態を正しく表している。
各記述の確度は `status` と仮説状態が示す。

## 3. 仮説を検証する流れ

1. リーンキャンバスの枠に沿って `HYP-` を立て、危険なものは `Q-`／`RISK-` に結ぶ。
   検証方法は問わない。検証の活動そのものと中間生成物は文書に残さない。
2. **実証**されたら、対応先（`vision` / `goals` / `actors` / `spec` の `RULE-`）へ本体を昇格し、
   [hypotheses.md](hypotheses.md) は要約と参照に落とす。
3. **反証**されたら、`decisions/` に学びを記録し、依存する記述を撤回する。

要求層で合意できることの条件は、テスト可能な粒度ではなく
**反証可能な仮説と検証方法があること**である（[文書体系 §1.2・§6.4](../README.md)）。

## 4. 決定が出たときの流れ

1. `product/decisions/` に決定を 1 ファイルとして記録する（`ADR-nnnn`）。
2. 業務ルールなら [spec/rules.md](../spec/rules.md) へ移す。`RULE-UI-` は識別子参照に置き換える。
3. 該当するユースケース・画面の記述を更新する（`status` の扱いは [文書体系 §5.5](../README.md)）。
4. [open-questions.md](open-questions.md) から当該 `Q-` を除く。

**見送り・先送りの決定は `Q-` を消費しない。** 「いまは作らない」と決めても、
その `Q-` が問うている業務判断は未回答のまま残る。`Q-` を除くのは**問いに回答が出たとき**だけであり、
見送りの決定は `decisions/` に記録して、`Q-` はその `ADR-` の**再訪条件を監視する対象**として残す
（[文書体系 §6.3](../README.md)）。現在の [ADR-0001〜0003](decisions/) と
[Q-28 / Q-21 / Q-20](open-questions.md) がこの関係にある。

**決定の記録だけは理由を残す。** 同じ議論を繰り返さないためであり、経緯の記録ではない。
要求層でこの例外に置けるのは、**反証された仮説・ピボット・見送ったストーリーの三種に限る**
（[文書体系 §6.2](../README.md)）。

## 5. 決定の記録の書式

```markdown
# ADR-0001 — （決めたことを一文で）

| 項目 | 内容 |
| --- | --- |
| 対象 | Q-nn / HYP-nn / STORY-nn |
| 決めた人 | |
| 影響する文書 | |

## 決めたこと
## そう決めた理由
## 採らなかった案とその理由
```
