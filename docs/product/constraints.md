# 前提と制約

設計・生成が従うべき前提。**AI へのコンテキストとして直接効く**ため、要求層に置く。
このうち「外から観測でき、テストできる」水準に落ちるものは `spec/non-functional.md`（`NFR-`）へ
移し、ここからは参照する（同じ事実を二か所に書かない／README §6.1）。

## 1. 利用者と規模

- **利用者のリテラシ** … 一般消費者。訓練・マニュアルを前提にしない。
  スタッフは店主と数名で、管理画面は日々の業務の中で覚えられる範囲に収める。
- **同時アクセス数** … 小規模。ピークでも同時数十セッションを想定する。
  この規模では性能水準を規定しない（→ [NFR-PERF-01](../spec/non-functional.md)）。
  規模の想定が変わったら `NFR-` に昇格させる。

## 2. 業務の前提

- **代金の授受と配送はシステムの外**で行う。注文＝支払ではない
  （[ADR-0001](decisions/ADR-0001-defer-online-payment.md)、[Q-28](open-questions.md)）。
- **買取は 1 申込 1 冊**。現物は店に届いて検分される。
- **配送先は米国内**を前提とする（州は 50 州＋首都特別区の固定選択——[Q-27](open-questions.md)）。
- **通貨は単一**。税は単一税率 10% の固定で扱う。これは合意済みの簡略化である
  （[RULE-ORDER-03](../spec/rules.md)、[INV-MONEY-03](../design/domain/invariants.md)）。
- 古物商としての許認可・法定帳簿は**店側の運用**で満たす（システムの責務にしない）。

## 3. 技術・運用の前提

- **認証は外部認証基盤に委ねる**。パスワードを預からない（[EXT-AUTH](../spec/integrations.md)）。
- **個人情報**として預かるのは氏名・メール（外部認証基盤側）と配送先住所（本システム側）のみ。
  保護の水準は `NFR-SEC-` が定める（→ [non-functional.md §3.1](../spec/non-functional.md)）。
- **コスト感** … 月額のクラウド費用を最小限に抑える。単一インスタンス＋最小構成の DB とし、
  冗長化・自動バックアップ・NAT はコスト上限に劣後する
  （→ [NFR-AVAIL-01 / NFR-DATA-01](../spec/non-functional.md)、受容は [RISK-06](risks.md)）。
- **アクセシビリティ** … 規定しない（→ [NFR-A11Y-01](../spec/non-functional.md)）。
- **多言語** … 英語のみ（→ [NFR-I18N-01](../spec/non-functional.md)）。

## 4. 制約の変え方

前提はコスト・規模・法規の変化で動く。変えるときは理由を `decisions/` に記録し、
影響する `NFR-` と `RULE-` を更新する（[product/README §4](README.md)）。
