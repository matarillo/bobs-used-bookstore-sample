# ADR-0002 — R3 では通知（メール等）を持たず、進行の確認を画面に限る

| 項目 | 内容 |
| --- | --- |
| 対象 | STORY-20 / Q-21 / EPIC-RESALE |
| 決めた人 | 店主（プロダクトオーナー）とチーム |
| 影響する文書 | [vision.md 非ゴール](../vision.md)、[story-map.md §5.1](../story-map.md)、[integrations.md §4](../../spec/integrations.md) |

## 決めたこと

買取・注文の進行（承認、支払、出荷など）を顧客へ push で知らせる仕組みを持たない。
顧客は自分の申込一覧・注文一覧の画面で進行を確認する。

## そう決めた理由

- R3 の目的は「承認／却下だけで買取が成立するか」（HYP-05）の検証であり、
  通知はその検証の前提ではない——**顧客が見に来るかどうか自体が検証の一部**である。
- メール送達（送信基盤の契約、SPF/DKIM、バウンス処理）は片手間に足せる規模ではない。
- 初期の申込件数なら、滞留への声かけは店の運用（電話・店頭）で吸収できる。

## 採らなかった案とその理由

| 案 | 採らなかった理由 |
| --- | --- |
| メール送信基盤を契約して状態遷移ごとに通知 | R3 の便に収まらない。検証したい仮説より先に手段を作ることになる |
| 画面内のお知らせ欄（ログイン後に未読を表示） | 送達の問題は避けられるが、「見に来ない顧客」には届かない点が push と等価に解決しない。作るなら通知全体の設計と一緒にやる |

**再訪の条件**: 承認済のまま現物が送られてこないオファーが滞留し始めたとき
（[RISK-01](../risks.md)）。買取が中核である以上、このトリガは最優先で監視する
（[Q-21](../open-questions.md)）。
