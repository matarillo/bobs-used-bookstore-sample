# 確認事項

リバースエンジニアリングの過程で見つかった、**業務担当者に確認しないと決められない事項**の一覧。

各項目は「現行はこうなっている」という**事実**と、「だからこう問う」という**問い**からなる。
本書は改善提案の一覧ではない。**何が決まっていないかの一覧**である。

## 0. 使い方

| 段階 | やること |
| --- | --- |
| 1 | 優先度 **A** から読み合わせる |
| 2 | 決まったことを、該当ユースケースの記述に反映する |
| 3 | **業務ルールとして決まったものは [spec/rules.md](../spec/rules.md) へ移す**。`RULE-UI-` は識別子参照に置き換える |
| 4 | 「現行のままでよい」と決まったものも、**決めたこととして記録する**（同じ議論を繰り返さないため） |

全体の流れは [product/README §4](README.md) が定める。
**見送り・先送りの決定は `Q-` を消費しない。** 「いまは作らない」と決まっても、
その `Q-` が問うている業務判断は未回答のまま残り、`ADR-` の再訪条件を監視する対象として
ここに残る（[文書体系 §6.3](../README.md)）。
[ADR-0001](decisions/ADR-0001-defer-online-payment.md)（Q-28）・
[ADR-0002](decisions/ADR-0002-defer-notifications.md)（Q-21）・
[ADR-0003](decisions/ADR-0003-defer-counter-offer.md)（Q-20）がこれに当たる。

| 優先度 | 意味 |
| --- | --- |
| **A** | 合意なしに実装・変更を進めると手戻りになる |
| **B** | 業務判断が要る。当面は現行どおりでも運用できる |
| **C** | 使い勝手・記述の一貫性の問題。まとめて処理してよい |

## 2. 詳細

### Q-01 — かごは誰のものか

**現行**: かごはブラウザに 1 年間保持される識別子で特定される。ログインしても、その識別子があればそのまま使われる。

**問い**

- 未ログインで入れた本は、ログイン後も残るべきか（現行：残る）
- 別の端末でログインしたとき、かごは引き継がれるべきか（現行：引き継がれない）
- 家族で 1 台のブラウザを共有し、別々にログインした場合、**かごを共有してしまう**が、それでよいか

**影響**: [UC-CUST-04〜12](../spec/use-cases/customer-browse.md)、`AGG-CART`（かご相関識別子の意味そのもの）

### Q-02 — 顧客は自分の情報にたどり着けない

**現行**: 住所の一覧へはヘッダの利用者名から到達する。氏名は外部認証基盤から取り込まれ、画面から編集できない。

**問い**: 「マイページ」に相当する場所が要るか。顧客が自分で氏名を直せる必要があるか。

### Q-03 — 検索は何を探すのか

**現行**: 検索語の照合対象・照合方式が**どこにも定義されていない**（ドメイン未定義）。並べ替えは書名・価格の 2 種。

**問い**

- 探す対象は書名だけか。著者・ISBN・概要も含むか
- 部分一致か、単語単位か
- 分類（ジャンルなど）で絞る手段は顧客側に要らないか（管理側にはある）

**影響**: 顧客がもっとも多く使う画面の中心的な振る舞い。**決まらないと検索は作れない。**

### Q-04 — 書籍詳細に書籍種別が出ない

**現行**: 分類 4 軸のうち、書籍詳細に出るのは出版社・ジャンル・コンディションの 3 軸。書籍種別（ハードカバー／ペーパーバックなど）が出ない。

**問い**: 中古書籍では購入判断に効くはずだが、意図的な省略か。

### Q-05 — 「売れ筋」とは何か

**現行**: トップに 4 件出る。**何をもって売れ筋とするかの定義がない**（ドメイン未定義）。

**問い**: 集計の期間（累計か直近か）、集計の単位（冊数か金額か）、件数。

### Q-06 — 「かごに入れる」操作の作法

**現行**: かご・欲しい物への投入だけがリンク操作であり、他の状態変更操作と作法が異なる。

**問い**: 他の操作と揃えるか。揃えると誤操作（ブラウザの戻る・再読込による重複投入）を防げる。

### Q-07 — 業務上の失敗をどう伝えるか

**現行**: 想定内として扱われているのは、入力検証・注文確定・画像判定のみ。それ以外の業務上の失敗は**すべてエラー画面に落ちる**。

具体例:

| 起きること | 現行 |
| --- | --- |
| 出荷済の注文を顧客が取り消そうとした | エラー画面。理由は伝わらない |
| 別のスタッフが先に処理したオファーを操作した | エラー画面 |
| 他人の住所を更新しようとした | エラー画面 |
| 二重送信でかごの明細を 2 回消した | エラー画面 |

**問い**: どこまでを「その場で伝える」に格上げするか。**すべてを格上げする必要はない**が、
現場が日常的に踏むもの（同時操作の競合）は伝えないと運用できない。

**影響**: すべてのユースケースの異常系。**横断的な方針として最初に決めるべき。**

### Q-08 — 注文の取消をどう扱うか

**現行**

- 「取消」ボタンは**状態にかかわらず常に出る**
- **確認ダイアログがない**。押した瞬間に取り消される
- 成功しても**通知が出ない**
- 出荷済・配達済・取消済なら失敗し、エラー画面に落ちる
- 他人の注文番号を指定した場合は**何も起きずに成功扱い**になる

**問い**

- 取り消せない注文にボタンを出さないようにするか
- 確認を挟むか
- 出荷後の取消要求（顧客からの申し出）は、業務としてどう受けるのか

### Q-09 — 件数が増えた一覧をどうするか

**現行**: 自分の注文・自分の住所・自分の買取申込・かご・欲しい物リストにはページ送りも並べ替えもない。並び順の取り決めもない。

**問い**: 常連客の注文が 100 件を超えたときの見せ方。新しい順に並べるべきか。

### Q-10 — オファー一覧の絞り込みが不完全

**現行**

- 絞り込んだ後、**条件が入力欄に残らない**（結果は正しく絞られる）
- **申込日で絞る条件がない**。ダッシュボードの「今月の申込」から辿っても全件が出る

**問い**: 不具合として直す前提でよいか。申込日の絞り込みは必要か。

### Q-11 — 金額の書式が画面ごとに違う

**現行**: 多くの画面は通貨書式だが、注文手続き画面と注文完了画面だけ通貨記号が固定されている。

**問い**: 単一通貨（[INV-MONEY-03](../design/domain/invariants.md)）の前提を変える予定はあるか。なければ書式を揃える。

### Q-12 — 空の一覧の見せ方が揃っていない

**現行**: 「見つかりません」と言う画面、空の表を描く画面、内容と噛み合わない文言を出す画面が混在する。

**問い**: 空のときに何を言い、次に何をさせるか（例：かごが空なら「本を探す」へ誘導する）。

### Q-13 — かごに入れたあと検索条件が失われる

**現行**: 書籍詳細から「かごに入れる」と、**条件なしの検索画面**に戻る。探し直しになる。

**問い**: 元の検索結果に戻すべきか、詳細画面に留まるべきか。

### Q-14 — かごの数量と在庫の見せ方

**現行**

- 数量は常に 1 ずつ増える。**画面から数量を指定・変更できない**
- 同じ本を 2 回入れると数量が 2 になるが、**画面上の見え方が変わらない**ため気づきにくい
- 在庫を超える数量も入れられる（在庫の判定は注文確定時）
- 書籍詳細画面は**在庫の状態を示さない**。在庫切れでも「かごに入れる」が押せる

**問い**

- 数量の変更手段が要るか（要るなら在庫数との関係をどうするか）
- 在庫切れの本を、かごに入れられるままにするか

### Q-15 — 何も起きていないのに「しました」と言う

**現行**: すでに欲しい物リストにある本を再度入れる／空のリストで「すべてかごへ移す」を押すと、
**何も変わらないのに「しました」と通知される**。

**問い**: 「すでに入っています」と伝えるべきか。

### Q-16 — 「残りわずか」のしきい値

**現行**: かご画面が、残り 5 冊以下の書籍に赤字で警告を出す。この 5 は画面が独自に持っている。

**問い**: 仕入判断の在庫僅少しきい値（[RULE-STOCK-04](../spec/rules.md)、同じく 5）と**同じ概念か**。

- 同じなら、ドメイン側の値に一本化する
- 違うなら（「補充が要る本」と「顧客を急かす本」は別の問い）、**別の名前と別の値**を与える

### Q-17 — 顧客に見せる金額はどれか

**現行**: 同じ買い物について、画面ごとに違う額が出る。

| 画面 | 出る額 |
| --- | --- |
| かご | 明細の小計の合計（**在庫切れも含む**、税抜） |
| 注文手続き | 小計の合計（**在庫切れを除く**、税抜） |
| 注文一覧 | 小計（税抜） |
| 注文詳細 | **合計（税込）** |
| 管理側の注文詳細 | 小計・税・合計の 3 段 |

**問い**

- 顧客が注文前に見る額に税を含めるか（現行は含めない。**注文後に増える**）
- 送料の概念を持つか（現行はない）
- かご画面で在庫切れ分を合計に含めるか

**あわせて確認**: 3 冊のうち 1 冊が在庫切れのとき、**残り 2 冊で注文を成立させる**のが現行である。
「全部揃わなければ注文しない」を選ぶ業務もありうる。

### Q-18 — 住所の「削除」の意味

**現行**: 削除は選択肢から外すだけで、記録は残る。その住所を使った注文は、削除後も配送先を参照できる。

**問い**: 顧客への説明をこれに合わせるか（「今後は使わない」など）。

### Q-19 — 顧客の注文詳細に配送先が出ない

**現行**: 管理側の注文詳細には配送先が出るが、顧客側には出ない。

**問い**: 顧客が「どこに届くか」を後から確認できなくてよいか。

### Q-20 — 買取価格は誰が決めるのか

**現行**

- 顧客が希望買取価格を**自分で入力する**（0 円〜1,000,000 円）
- 店にできるのは**承認か却下だけ**。金額を変えて提示し直す手段がない
- **買取価格の算定基準はどこにもない**（ドメイン未定義）

**問い**

- 実務では店が査定して値を決めるのではないか。そうなら「店が金額を提示する」段階が要る
- 0 円での申込を許すか
- 上限 1,000,000 円に根拠はあるか

**影響**: 買取の流れの形そのもの（`AGG-OFFER` の状態遷移が増える可能性がある）。

### Q-21 — 買取の進行を顧客にどう伝えるか

**現行**

- 承認されると状態が「承認済（発送待ち）」になる。**顧客は本を送らなければならないが、画面は何も促さない**。送り先も示されない
- 通知（メールなど）の仕組みが**まったくない**
- 却下されても**理由が伝わらない**
- 顧客は申込を**取り下げられない**
- スタッフ側にも「承認済のまま何日経過したか」を見る手段がない

**問い**: 買取の流れを実際に回すために、どの段階で・誰に・何を伝えるか。

**影響**: 買取が中核サブドメインである以上、**ここが動かないと事業が回らない**。

### Q-22 — 画面の言葉と用語集が食い違う

**現行の例**

| 画面の言葉 | 用語集での意味 |
| --- | --- |
| 「発送を確認」 | **受領確認済**（店が現物を受け取った） |
| 注文一覧の「Total Cost」 | **小計**（税抜） |
| 「Low stock」（在庫僅少） | 在庫 0 を**含む** |

**問い**: 画面を用語集に合わせるか、用語集を現場の言い方に合わせるか。
**どちらでもよいが、揃っていないことが問題である**（同じものを違う言葉で呼ばない）。

### Q-23 — 注文の後戻りと配送の記録

**現行**

- 状態は前にしか進まない。**出荷を取り消せない**
- **返品・返金の概念がない**
- スタッフから注文を取り消す手段がない（顧客だけができる）
- 追跡番号・配送業者・実際の出荷日を記録しない

**問い**: 中古書店の実務でこれらがどの程度起きるか。起きるなら、どう記録するか。

### Q-24 — 在庫と原価をどう記録し、何を見せるか

**現行**

1. **手入力した書籍は仕入原価を持たない**。売れても粗利の計算から除外される（0 として数えるのではなく、**分からない**）
2. 書籍の更新画面から**在庫数を直接書き換えられる**。棚卸しには要るが、注文による増減と手による修正の区別が記録に残らない
3. 管理側の書籍詳細に**在庫数が出ない**（一覧には出る）
4. 在庫 0 の書籍を**カタログから消す手段がない**。売り切れた本が検索結果に残り続ける

**問い**

- 手入力の書籍にも仕入原価を入れさせるか（入れれば粗利が正しく出る）
- 在庫の直接修正を残すか。残すなら理由を記録するか
- 売り切れた本を隠す／廃棄する手段が要るか

### Q-25 — 参照データの保守が片道である

**現行**

- 書籍編集画面から分類を「追加」すると、**書籍編集画面に戻ってこない**。入力中の内容が失われる
- **名称の重複を検査しない**。同じ出版社を二重に登録できる
- **入力を検証していない**。空の名称を送るとエラー画面に落ちる
- 使わなくなった項目を**廃止できない**
- 一覧が 0 件のとき「更新はありません」と、内容と噛み合わない文言が出る

**問い**: 分類の選択肢は誰がいつ増やすのか。運用の頻度によって、直すべき順序が変わる。

### Q-26 — 注文完了画面に注文番号がない

**現行**: 注文完了画面は「注文を承りました」と品物の一覧だけを出す。
**注文番号・合計金額・納品予定日を表示していない。**

**問い**: 顧客が問い合わせるときに何を伝えればよいのか。注文番号を出すべきではないか。

### Q-27 — 住所は国内向けか国外向けか

**現行**: 州は米国 50 州＋首都特別区の固定選択。一方、国は自由入力。郵便番号は数字のみ。

**問い**: 国外への配送を想定するか。しないなら国を固定し、するなら州の扱いを見直す必要がある。

### Q-28 — お金の受け渡しを記録しないでよいか

**現行**

- **注文に決済の概念がない**。金額は算出されるが、支払われた事実を記録しない。「注文した ＝ 支払った」ではない
- 買取の「支払う」は、**支払った事実の記録**であって送金ではない。支払方法・支払先も記録しない

**問い**: 代金のやり取りをどこで行い、どこまでをこのシステムに記録するか。

### Q-29 — ダッシュボードの数字は信じてよいか

**現行**

| 事項 | 状態 |
| --- | --- |
| 「今月の注文数」「今月の申込数」の基準日 | **未定義**。記録の作成日時に依拠している |
| 「在庫僅少 N 冊」のリンク先 | 件数と一覧が**一致しない**（指標は在庫切れを含まないが、絞り込みは含む） |
| 「今月の申込 N 件」のリンク先 | 絞り込みが**効かない** |
| 統計が取得できないとき | **すべて 0 と表示**され、取得失敗と区別できない |
| 納品予定日の「7 日」 | **根拠のない定数** |
| 在庫僅少の「5」 | **根拠のない定数** |

**問い**: どの数字を意思決定に使うのか。使う数字だけでも定義を固める。

### Q-30 — 売価を決める材料がない

**現行**: 棚入れ画面は仕入原価しか示さない。同種の本の相場も、過去の売価も、粗利の見込みも出ない。

**問い**: 値付けは何を見て決めているのか。その材料を画面に出せるか。

### Q-31 — スタッフの役割は一種類でよいか

**現行**: 管理画面の権限は単一である。管理者グループに属していれば、在庫・買取・注文・参照データ・ダッシュボードのすべてを操作できる。

**問い**: 「支払を記録できるのは誰か」「売価を決められるのは誰か」に区別が要るか。
お金が動く操作（支払の記録、売価の決定）は、分けたくなることがある。
